# 醫療病歷質控 Copilot 客戶需求說明

依據[需求來源](../../../../Raw/confirmed-requirements/customer-requirements/客戶需求.md)整理，供需求分析、方案討論與 Playground 使用。數據範圍和使用條件見[醫療數據說明](../../../../Data/醫療病歷質控/README.md)。

<a id="req-med-001-01"></a>
## REQ-MED-001-01 產品定位、責任與人工確認

來源定位：[原始文件](../../../../Raw/confirmed-requirements/customer-requirements/客戶需求.md#req-med-001-01)第 10—20 行；依據條目 286, 287, 288, 289。

業務問題：通用 AI 直接給出結論或改寫記錄時，使用者難以區分輔助建議與已承擔責任的專業決定，也難以知道應由誰複核。

產品定位為“病歷質控、證據定位與整改協同 Copilot”。系統提出疑似問題、展示證據、組織複核與協作；不自動診斷，不在無人確認時修改病歷，不代替醫生或專家承擔最終專業責任。醫生負責病歷內容及解釋，質控人員複核質量問題，信息科管理接入與數據邊界，管理部門接受業務責任和放權範圍，供應商承擔工具實現、可追溯與故障處置職責。

預期效果：使用者能夠識別“系統發現—人工複核—責任接受”的區別。

<a id="req-med-001-02"></a>
## REQ-MED-001-02 一期場景與產品形態

來源定位：[原始文件](../../../../Raw/confirmed-requirements/customer-requirements/客戶需求.md#req-med-001-02)第 21—31 行；依據條目 290, 309。

一期覆蓋單一內科病區、成人肺炎住院病歷，檢查出院前文書完整性與前後記載一致性；圍繞 8 條文書質控規則貫通完整協作流程。病種僅用作資料篩選標籤，不設計自動診斷或臨床用藥判斷。

一期採用獨立工作臺及離線文件導入，集中呈現證據和責任鏈；標準 API/SDK 作為集成邊界設計，HIS 內嵌作為形態比較與後續接入討論。三種形態共享身份、來源定位、複核與審計要求，當前不存在已接通的醫院系統。

不自動擴展至全院、所有病種、全部現有規則或影像/心電自動診斷。超出病種、科室、語言、規則版本或證據能力的輸入明確進入範圍外/待人工判斷。規則表見業務約定 AGR-MED-001-02。

<a id="req-med-001-03"></a>
## REQ-MED-001-03 材料性質與證據用途分離

來源定位：[原始文件](../../../../Raw/confirmed-requirements/customer-requirements/客戶需求.md#req-med-001-03)第 32—42 行；依據條目 291。

業務問題：公開脫敏記錄、文獻病例、合成材料和生產證據混用，會讓測試結果被誤當成上線驗收依據。

每份輸入應帶來源類別、使用目的、授權範圍與版本。公開脫敏病例可用於離線研究；文獻病例敘述不是完整原始住院病歷；合成材料必須顯式標記，不能作為真實患者或生產效果證據；真實生產材料只有具備相應授權和實際採集記錄時才可如此標記。

已有資料範圍見數據 README。複核、申訴、整改前後版本、責任簽字和上線驗收記錄在實際流程中形成；每項驗收結果均須標明來源和證據等級。

<a id="req-med-001-04"></a>
## REQ-MED-001-04 病歷結構與醫療業務語義

來源定位：[原始文件](../../../../Raw/confirmed-requirements/customer-requirements/客戶需求.md#req-med-001-04)第 43—53 行；依據條目 292, 294。

業務問題：同一事件散落於字段、段落和檢查結果，長尾寫法、缺失字段或跨段矛盾使問題無法準確回指。

結構化保留病例/就診標識、文書及版本、原字段路徑、段落、時間表達、檢查結果和診療事件；規範化值必須鏈接原表達。醫療上下文圖連接這些對象與規則、問題、意見、整改版本，不預設圖數據庫產品。

保留罕見寫法、未知值、時間不確定性和矛盾，不用模型補齊事實；未記錄不等於臨床未實施，脫敏偏移時間不等於真實日曆。無法可靠關聯的事件保留未關聯狀態。預期效果是複核人能看見原始語境和結構化過程中的不確定性。

<a id="req-med-001-05"></a>
## REQ-MED-001-05 域內處理、最小數據與訪問審計

來源定位：[原始文件](../../../../Raw/confirmed-requirements/customer-requirements/客戶需求.md#req-med-001-05)第 54—64 行；依據條目 293, 310。

業務問題：病例被髮送到未批准服務、同崗位人員越權查看、日誌殘留全文，都會使功能效果與數據責任脫節。

敏感病歷正文、可還原身份的標識、證據片段與含敏感內容的嵌入按同一域內邊界處理；檢索、模型、日誌及備份均納入數據流說明。只傳遞當前任務必需字段，未授權的外部端點不接受數據。

按角色分配動作，再按科室、責任病例、任務歸屬、授權目的和有效期限制對象訪問。查詢、導出、複核、改派、規則變更及拒絕訪問均留可追溯記錄。數據保留期限按類別明確後再啟用生產留存，具體保留期限由相應責任部門確定。預期效果是授權行為和數據流可解釋、可追查。

<a id="req-med-001-06"></a>
## REQ-MED-001-06 規則、指南及生效版本治理

來源定位：[原始文件](../../../../Raw/confirmed-requirements/customer-requirements/客戶需求.md#req-med-001-06)第 65—75 行；依據條目 295。

業務問題：同一病例採用不同時間或適用範圍的規則，會出現看似相同卻無法重放的質控結論。

規則與知識依據分別記錄穩定編號、版本、發佈來源、適用病種/科室/人群/文書/語言、審批狀態、生效及失效時間。每次判斷固定病例版本、規則包版本和知識依據版本。廢止或衝突不能靜默替換；重跑形成新結果並保留舊記錄。

未核實版本、適用條件或批准狀態時，不把候選規則作為已生效規則。預期效果是能說明“當時為什麼這樣判斷”，並識別版本變化影響的病例。

<a id="req-med-001-07"></a>
## REQ-MED-001-07 規則、檢索、LLM 與專家分工

來源定位：[原始文件](../../../../Raw/confirmed-requirements/customer-requirements/客戶需求.md#req-med-001-07)第 76—86 行；依據條目 296, 297, 298, 299。

業務問題：可枚舉條件和專業爭議都交給同一種模型處理，會丟失可審計性或責任邊界。

確定性規則處理已明確、可枚舉、可審計的條件；知識檢索提供與版本和適用範圍相符的指南、規則解釋及依據；LLM 只給出跨段綜合、語義矛盾候選與結構化建議；專家處理爭議、例外、高風險結論與最終責任。

每條問題記錄由哪個環節產生、使用什麼輸入版本、哪些部分仍須人工判斷。規則通過不等於病歷整體合格，檢索命中不等於依據適用，模型推斷不自動晉升為專家結論。預期效果是專業判斷由適當責任主體完成。

<a id="req-med-001-08"></a>
## REQ-MED-001-08 問題—規則—原文—意見的證據契約

來源定位：[原始文件](../../../../Raw/confirmed-requirements/customer-requirements/客戶需求.md#req-med-001-08)第 87—97 行；依據條目 301, 302, 303。

業務問題：只有一句“存在問題”或整改建議，沒有原文和規則鏈路，醫生無法核查，質控人員也無法解釋。

每條疑似問題攜帶問題類型、建議嚴重度、規則編號與版本、判斷理由、整改建議、病例/文書版本、字段或段落定位、原文片段及校驗依據、知識來源、產生環節和複核狀態。嚴重度建議與人工確認值分開。

界面分層顯示來源事實、規則判斷、模型推斷、專家結論；支持從問題回到原文上下文與適用規則。定位缺失時顯式標記，不能製造字符偏移或拿整份文檔鏈接冒充精確證據。預期效果是複核與申訴圍繞同一版本的可檢驗證據展開。

<a id="req-med-001-09"></a>
## REQ-MED-001-09 不確定性分流與失敗關閉

來源定位：[原始文件](../../../../Raw/confirmed-requirements/customer-requirements/客戶需求.md#req-med-001-09)第 98—108 行；依據條目 300, 304, 305。

業務問題：無證據、規則衝突或模型不確定時仍推進，會把未知當作通過；一個未經校準的分數也可能掩蓋高風險。

證據不足、引用定位失效、規則衝突、範圍不適用或關鍵服務失敗時，停止自動通過、自動回寫和進入待簽字等推進動作，轉為待人工處理並說明阻斷原因。人工仍可查看已有證據、補充材料和裁決，禁止把安全阻斷等同於系統靜默丟棄任務。

確定性或風險信號只有在說明校準數據、方法、適用範圍和版本後才用於分流；未校準時顯示未校準/未知，不展示虛假的精確概率。任何分數不能替代規則和專家確認。預期效果是未知與失敗始終可見，並有明確恢復路徑。

<a id="req-med-001-10"></a>
## REQ-MED-001-10 複核、申訴、整改、再核驗與簽字閉環

來源定位：[原始文件](../../../../Raw/confirmed-requirements/customer-requirements/客戶需求.md#req-med-001-10)第 109—119 行；依據條目 306, 308。

業務問題：問題清單有了，醫生反饋和整改卻散在多處，系統無法證明爭議是否解決、修改是否對應新版本。

主流程為疑似問題→質控複核→醫生申訴或整改→再次核驗→責任簽字。質控可駁回誤報並留理由；醫生可接受問題並提交整改，也可申訴；專家裁決可撤銷問題、要求整改或升級爭議；再次核驗可通過或退回修改。每次重新提交形成新版本，不覆蓋舊意見和證據。

仍有未解決高風險問題、爭議、證據缺口或版本失配時不得進入簽字。簽字後的新病歷版本需要新的核驗/簽字流程，舊簽字僅對原凍結版本有效。預期效果是從發現到解決的過程和結論均可追蹤。

<a id="req-med-001-11"></a>
## REQ-MED-001-11 責任人、時限、權限與操作留痕

來源定位：[原始文件](../../../../Raw/confirmed-requirements/customer-requirements/客戶需求.md#req-med-001-11)第 120—130 行；依據條目 289, 307, 310。

業務問題：知道問題狀態卻找不到當前責任人，或者同一人越權修改、複核和代簽，使閉環失去責任意義。

任務記錄責任醫生、質控複核人、當前處理人、業務確定的截止時間、意見與版本；改派、延期、退回、接受、駁回、重新提交和簽字均記錄操作者、時間、理由及前後狀態。截止時間來源於任務約定，逾期只提醒或升級，不自動視為同意或代簽。

醫生處理授權病例，質控複核所屬範圍，專家裁決被指派的爭議；信息科管理接入與權限配置，管理部門確認准入範圍及接受責任，供應商不默認獲得生產病歷訪問權。預期效果是每個需要人處理的節點都找得到責任主體。

<a id="req-med-001-12"></a>
## REQ-MED-001-12 風險不對稱的評測與專家共識

來源定位：[原始文件](../../../../Raw/confirmed-requirements/customer-requirements/客戶需求.md#req-med-001-12)第 131—141 行；依據條目 311, 312, 313。

業務問題：總體準確率可能掩蓋高風險漏報；單人判斷或把模型生成參考標註當金標準，會放大不可靠結論。

按規則、嚴重度、數據來源、罕見寫法、缺失和跨段矛盾分層抽樣，由兩名獨立專業複核者給出判斷，分歧進入仲裁；保留原始判斷和一致性分析。規則召回、誤報負擔、證據定位可用性、解釋可用性和整改建議可用性分別統計，記錄分母、無效輸入和棄答，不能用剔除困難樣本抬高指標。

驗收集合中出現經專家確認的高風險漏報，阻止範圍晉級；零次觀察漏報不等於總體零風險。其他閾值需隨樣本與業務風險確認，結果以實際評測記錄為準。預期效果是放權依據對應具體風險和可複核證據。

<a id="req-med-001-13"></a>
## REQ-MED-001-13 關鍵人驗收、責任接受與漸進放權

來源定位：[原始文件](../../../../Raw/confirmed-requirements/customer-requirements/客戶需求.md#req-med-001-13)第 142—152 行；依據條目 314, 315。

業務問題：單次測試通過被當成上線許可，醫院與供應商對驗收版本、使用範圍和最終責任各有理解。

先做離線驗證，再進入限定範圍的影子運行；影子運行結果不作為臨床執行依據，不寫回病歷。只有評測證據、關鍵人驗收和責任接受記錄齊備後，才進入人確認的輔助決策；擴大科室、規則、病種或模型版本需重新評估受影響範圍。

准入記錄包含數據集、規則、模型、知識與應用版本、範圍、指標證據、未解決風險、參與崗位、簽署時間和回退條件。發現門禁失效時停止受影響能力並回到人工流程。預期效果是每一次放權都有範圍、證據和責任記錄。

<a id="req-med-001-14"></a>
## REQ-MED-001-14 跨案例複用與醫療資產沉澱

來源定位：[原始文件](../../../../Raw/confirmed-requirements/customer-requirements/客戶需求.md#req-med-001-14)第 153—163 行；依據條目 286, 316, 317, 318。

業務問題：照搬案例一的權限和自動化程度會越過醫療責任邊界，完全重做又丟失已形成的交付方法。

複用業務發現、系統調查、證據契約、評測與門禁的穩定組織方式；重新設定敏感數據邊界、專家複核、爭議仲裁、責任簽字和放權條件。逐項記錄“可複用骨架—醫療變化—驗證證據”，不將某院特殊規則固化為全部項目通則。

後續沉澱帶版本和來源的醫療規則包、角色/屬性權限模板、專家分層評測資產包及責任流程組件；區分通用資產、醫療域資產和醫院定製。當前只定義應交付內容，不宣稱已有可直接複用的生產代碼或已驗證醫學資產。
