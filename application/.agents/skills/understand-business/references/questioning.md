# 追問與業務認知方法

根據當前項目的信息缺口選擇方法，不逐項宣讀問卷。

## 怎樣選擇下一問

找出會改變角色、工作流程、痛點或輔助方式的關鍵未知，再看它的前提是否已經明確。能夠從資料查清的先查，只有人的意圖、取捨或資料外事實需要提問。

一輪交流按需要包含三件事：已有理解和依據；為什麼這個缺口影響當前判斷；一個能用自然語言回答的問題。不要只拋出“業務本體”“責任模型”等名詞讓新手自行理解。

只有用戶卡住或確實需要選擇時才給少量選項，允許自由表達及“不知道、待核實”。多項回答一併吸收，避免重新詢問已經提供的信息。

## 不同反饋的處理

| 情況 | 繼續方式 |
| --- | --- |
| 資料已經回答 | 展示與當前問題有關的發現和位置，繼續處理資料無法解釋的部分 |
| FDE 不懂術語 | 用日常工作解釋它與相近概念的差別，然後回到原問題 |
| FDE 不知道實際做法 | 檢查現有記錄；仍未知就保留缺口、核實對象和影響，不反覆逼答 |
| FDE 只說“想自動化” | 討論希望減少哪項工作、結果給誰使用、哪個環節仍需判斷 |
| 用戶讓 AI 推薦 | 給出有理由的建議和影響，保留建議身份，不補造項目事實 |
| 來源與回答矛盾 | 並列說明衝突及適用條件，核對版本或當事方；未解決就保持待核實 |
| 用戶問“為什麼要問這個” | 結合本項目資料與工作說明它會影響什麼，不啟動另一輪問卷 |
| 用戶要求先整理 | 基於已發生的討論落盤，準確標明缺口，不用虛構信息補滿結構 |
| 話題開始發散 | 判斷與當前業務目標的關聯；不影響本輪理解的分支先不展開 |

## 把模糊想法落到具體工作

以下僅為問法示例，具體對象、時間和規則必須來自當前資料：

- “你提到跟進費時間。記錄裡能看到最近一次是誰把什麼交給了誰嗎？”
- “這裡的‘完成’是做完、交出，還是對方確認收到？資料是否區分了這些狀態？”
- “這份表記錄了處理時間，但還解釋不了超時原因。我們先看哪個環節最容易卡住？”
- “這條建議希望幫助誰作判斷？他需要同時看到哪些依據？”
- “希望改善的是重複操作，還是發現問題的能力？這會影響我們考慮的輔助方式。”

先幫助用戶理解問題，再邀請補充信息。一次回答解決了多個問題，就推進剩餘缺口，不重複執行整套問法。

## 解釋、證據與假設

常見行業做法只能作為背景知識或候選解釋，不能直接寫成該企業的制度。需要補充專業知識時，先查已有資料，再按授權檢索可靠原始來源；不能把敏感原文傳給外部服務。

FDE 可以認可自己的理解稿或選擇討論方向，但這不代表客戶接受了規則、責任、時限或指標。無法從現有資料核實的內容進入待確認事項，留給後續原型討論及相關業務方核實。

數據讀取只支持實際觀察。例如看到多份記錄含“處理人”字段，能說明系統保留了這個字段；不能因此斷定該人擁有審批權。把這類推斷轉成可核實的問題。

## 何時收斂

能夠講清關鍵工作、參與者、困難和預期，且事實與假設分明時，可以形成資料初稿。剩餘未知應有明確影響和核實方向。再問一個問題若只增加細節而不改變當前理解，就不必繼續追問。

不以問過多少輪或模型給出的清晰度分數作為完成證明。原型、客戶確認和實際業務驗證屬於後續工作，不能由本輪對話自動替代。
