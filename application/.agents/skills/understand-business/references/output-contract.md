# 獨立資料包的輸出結構

本契約內置了後續需求 Playground 所需的資料發現方式：**索引 → 按主題選擇正文 → 穩定條目 → 原始依據**。本技能直接生成這些 Markdown 資料，不需要運行 Playground、需求規範化 Skill 或看板腳本。

## 目錄與入口

默認相對於目標項目根目錄寫入 `docs/01_business-understanding/`。用戶指定的位置優先；已存在本次業務的同用途資料包時原位更新。與原始文件分開，不覆蓋已有已確認需求，不因編號類似而遷移其他階段目錄。

```text
docs/01_business-understanding/
├── index.md
├── 客戶需求/
│   └── 業務需求理解.md
├── 業務約定/
│   └── 業務邊界與待確認規則.md
└── 溝通記錄/
    └── FDE業務討論.md
```

文件名可按實際主題調整。三類資料歸在同一父目錄；沒有內容的類別不預建空目錄或空文檔。目錄名“客戶需求”不代表客戶已經確認，正文與元數據必須說明實際來源和狀態。

### `index.md` 必須說明什麼

- 本輪業務背景、當前階段、資料範圍和成熟度，例如“FDE 業務理解草案”。
- 如何按當前問題讀取關聯文件，不要求後續 Agent 通讀所有內容。
- 文檔清單：穩定編號、相對文件鏈接、資料類型、來源性質／狀態、覆蓋主題、適合回查的問題。
- 待核實、衝突和未讀取資料的入口及影響，不把尚未讀取的資料算成已理解。
- 後續使用說明：製作需求 Playground 時先讀取本索引，再讀取相關正文；保留假設、建議與未確認狀態。

索引提供路由，不替代業務正文。不要只列標題、文件路徑或網絡鏈接，而沒有寫出已形成的理解。

## 各類正文承擔什麼

| 類型 | 正文內容 | 需要保留的區別 |
| --- | --- | --- |
| 客戶需求 | 背景、角色目標、現狀與痛點、擬議輔助能力、預期效果、討論範圍 | 來源明確的客戶訴求、FDE 的理解和方案建議分別標註 |
| 業務約定 | 對象、規則、適用條件、權限、責任、例外及待確認邊界 | 已有規則與擬議規則分開；未知不補造 |
| 溝通記錄 | 實際發生的 FDE 問答要點、資料觀察、解釋、修正、決定與未決事項 | 明確是 FDE 與 Codex 的討論，不偽裝成客戶或專家訪談 |

在需求正文中按實際內容講清“誰在什麼工作中遇到困難 → 擬用什麼能力輔助 → 預期改善什麼”。該關聯幫助後續看板提煉內容，不是提前定義系統菜單，也不是正式 Feature Spec。

## 元數據與條目定位

正文使用 YAML frontmatter。字段示意如下，不能將示意佔位值作為真實交付：

```yaml
---
id: BU-REQ-001
type: 客戶需求
origin_kind: analysis
source: "相對於本文件的來源路徑；或如實說明來自本次 FDE 對話"
source_sha256: null
source_date: null
participants: []
topics: [角色, 現有工作, 痛點, 預期]
status: FDE理解草案
---
```

- `id` 穩定且在資料包內唯一；建議用 `BU-REQ`、`BU-AGR`、`BU-INT` 區分三類，避免冒用原客戶文檔編號。
- `origin_kind` 使用 `document`、`conversation` 或 `analysis`，說明主要來源。綜合多個來源時在正文逐條列明。
- `source` 鏈接實際來源文件或如實註明對話來源。來源是可讀取的原始文檔時，`source_sha256` 寫真實字節校驗值；對話沒有文件就用 `null`，不能編造文件路徑或摘要。
- `source_date` 是原記錄明確的業務日期，不用文件修改時間代替；不知道就用 `null`。整理日期如需記錄可另寫。
- `participants` 只寫已知身份或姓名，不補造客戶、醫生或專家。
- `status` 如實表達來源確認情況；整份理解稿得到 FDE 認可，也不代表其中每項規則已經被客戶批准。

正文用穩定的條目標識與錨點，方便後續引用：

```markdown
<a id="bu-req-001-01"></a>
## BU-REQ-001-01 當前工作與困難

性質：資料事實／FDE 陳述／分析假設／方案建議（選實際適用者）。
依據：實際文件及章節、數據記錄定位，或本次討論中的具體問題與回答。
確認狀態：按實際填寫。

這裡寫已形成的業務理解、理由和適用條件。
```

以上是格式說明，不生成空條目。資料中明確的數字、條件、否定詞與責任保留原意；來源無法證明的判斷保持假設狀態。問答摘要註明是整理摘要，不偽裝成逐字原話。

## 數據觀察的落盤

原始數據庫、JSONL、表格和圖片留在原位置。把與業務理解有關的實際觀察寫入溝通記錄，記錄文件、表或工作表、字段、記錄標識、讀取範圍及可用版本信息；不把原始數據複製成一套新資料。

摘要只表達樣本真正支持的判斷。沒有全量核驗就說明範圍，不根據少量樣本宣稱統計覆蓋；來源觀察、業務解釋和待核實關係分別記錄。

## 對項目入口的最小補充

生成資料包後，在目標項目 `AGENTS.md` 增量添加實際存在的索引鏈接、用途和狀態。例如：

> 業務理解資料入口：`docs/01_business-understanding/index.md`。本輪為 FDE 理解稿；後續製作 Playground 或核對業務理解時按索引讀取相關正文，保留待確認事項。

實際文件中的路徑應可點擊且相對於項目根目錄。保留已有客戶材料、已確認需求與原型入口；不要用探索稿取代已有依據，不寫全局指令。

## 完成與交接

檢查索引能定位正文，正文能定位所用來源；條目 ID 和錨點一致；事實、假設、建議和確認狀態沒有混淆；沒有憑空生成客戶訪談或業務規則。

交付資料索引、正文數量與類型、重要待核實項，並說明後續 Playground 應讀取哪個入口。HTML 和 `board-data.json` 屬於後續看板工作流，不是本技能的交付。一次生成完成不等於人工已經認可業務理解。
