# 業務理解與追問

幫助 FDE 基於已有資料建立業務認知，藉助有針對性的解釋和追問，逐步形成可追溯的業務理解資料。對話對象是 FDE；FDE 的理解、模型的分析與客戶已經確認的事實必須區分。

本技能獨立運行，內置追問方法與資料格式。**終點是可供 Playground 讀取的 `index.md` 和索引指向的業務正文文件。** 不調用 `playground`、看板生成器或其他需求整理工作流，不生成 `index.html`、`board-data.json`、原型或產品規格。後續工具由用戶另外安排。

## 先明確背景並讀取資料

1. 讀取目標項目的 `AGENTS.md` 與資料入口，結合當前對話明確業務背景、當前階段、已有資料和希望補齊的理解。用戶已經說過的信息直接利用；只有目標項目或關鍵背景仍無法判斷時才問清。
2. 優先讀取已有業務理解索引、用戶指定材料和相關段落。數據按當前問題查看字段及有限樣本，大文件按需讀取，不為開始討論而遍歷或複製整個數據集。無法讀取或尚未查看的材料如實標明。
3. 區分資料能證明什麼：字段與記錄可以支持對數據和事件的觀察，不能單獨證明崗位職責、客戶痛點、業務因果或授權。原始文件只讀，觀察結果保留文件及記錄定位。
4. 簡短複述當前理解和最重要的信息缺口，再進入追問。已有資料能夠回答的事實先自行查找，不把查資料的工作交回給 FDE。

## 按缺口選擇討論角度

以下角度用於判斷下一問，不是必須逐題完成的調查表：

| 角度 | 需要理解的內容 |
| --- | --- |
| 角色與目標 | 誰做事、為誰服務、希望完成什麼、誰決定或確認 |
| 現有工作 | 觸發情境、業務對象、主要步驟、崗位交接、當前工具和替代做法 |
| 數據與證據 | 資料在什麼環節形成、記錄什麼、支持什麼判斷、缺失或衝突在哪裡 |
| 痛點與影響 | 哪一步遇到困難、如何影響工作、哪些判斷仍是假設 |
| 輔助方式 | 希望系統幫助完成什麼，人員還需要判斷什麼，結果需要哪些依據 |
| 邊界與預期 | 本輪覆蓋範圍、責任和約束、期待的改善及需要繼續核實的事項 |

行業差異從本項目資料和對話中識別。醫療、製造、電商等案例可以改變術語、規則、數據和責任邊界，不改變這套理解業務的方法；不要把某個案例的制度寫成通用規定。

## 輔導式追問

具體分支見 [追問方法](references/questioning.md)。

- 每輪優先推進一個重要問題，說明已有依據和為什麼要問；用戶一次給出多項信息時全部吸收，不拆成重複問題。
- 前提未明確時先解決上游問題，例如先區分業務對象，再討論它的流轉，不直接要求選擇技術架構。
- FDE 不懂概念時先用日常工作解釋；不知道事實時先找資料，仍未知就記錄缺口和核實方向。可以舉少量可能情形幫助理解，但必須標為示例或假設。
- 知識可以解釋，事實需要依據，業務取捨需要人表達意圖。用戶讓 AI 推薦時給出理由和影響，不能把推薦或沉默當成確認。
- 對每輪迴答更新當前理解；發現資料與陳述衝突時指出來源和影響，不靜默選擇其中一個。背景改變後只重新核對直接受影響的判斷。
- 始終圍繞本項目的問題與當前階段。參考方法中的完整開發流程、評分體系或技術選型不自動進入本輪討論。
- 用戶插入解釋、暫停或方向調整時先回應，恢復後接著未解決的問題。不要為了固定輪數持續追問。

實質發現和決定逐步記入同一批資料，保留原始來源、FDE 陳述、分析假設、擬議方案和待核實事項的身份。沒有發生的客戶訪談、沒有得到的專家意見、沒有給出的指標不得補造。

## 獨立生成資料包

當已經可以解釋主要角色、關鍵工作、困難與預期，並能明確標註剩餘未知時，整理一版資料供 FDE 校驗。用戶要求先形成草案時，按已有依據落盤，不要求所有問題都解決。只有足以改變當前業務理解的缺口才繼續追問。

1. 讀取本技能內置的 [輸出結構與字段](references/output-contract.md)，確定本次唯一輸出目錄。默認使用項目內 `docs/01_business-understanding/`；已有本次業務的同用途入口就原位更新。原有已確認需求索引不被本輪探索資料替換。
2. 根據實際內容整理需求理解、業務約定或待確認邊界、FDE 溝通記錄；沒有內容的類別不湊文件。每份正文包含理解結果、實際依據、適用條件和確認狀態，不能只交付空模板或鏈接清單。
3. 寫入 `index.md`：說明當前背景與成熟度，逐項鍊接正文，並列出主題、適合回查的問題和待核實項。後續 Agent 應能從索引找到相關事實及原始依據，無需重新依賴整段聊天。
4. 在目標項目 `AGENTS.md` 中補充這一實際入口及“FDE 理解稿，尚不等於客戶確認”的用途。保留現有有效資料入口；不復制本技能全文或全部業務內容進項目指令。
5. 核對文件鏈接、條目編號、來源定位及狀態，確認需求正文能夠支持後續梳理“痛點 → 擬議功能 → 預期效果”。不提前替後續工具渲染看板或生成其內部數據文件。

資料不足時準確寫出缺口；對尚未成立的痛點或方案保持“待核實／建議”狀態。不能為了讓目錄顯得完整而假裝完成了需求確認。

## 交付、校驗與迭代

交付可點擊的資料索引、關鍵正文和一句後續使用說明：後續製作 Playground 時，以這個索引為資料入口，按主題讀取關聯文件。明確本輪仍未知或未確認的事項。

由 FDE 檢查角色和工作流程是否理解正確，痛點與建議是否對應，邊界和預期是否符合想法及現有業務。收到反饋後，修訂對應正文、狀態與索引，保留穩定編號和真實來源；不每輪新建一套資料。

若實際使用暴露了 Skill 的定義或問法問題，指出具體偏差與修改建議。用戶要求更新 Skill 後才修改通用規則；項目特定事實留在業務資料中。方法來源與融合取捨見 [參考說明](references/method-sources.md)，無需在運行時安裝或調用這些外部 Skills。
