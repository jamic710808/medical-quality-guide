# 實施合同、驗證與交接

## 在項目中固定的技術合同

| 內容 | 最小需要說明 |
| --- | --- |
| 節點 / 工具 | 輸入輸出、只讀/寫入、授權範圍、證據、超時/錯誤、冪等鍵及是否可重放 |
| 狀態與版本 | 業務對象版本、運行/attempt/thread/checkpoint、圖/配置版本；數據分別由誰維護 |
| 人工交接 | 要求的崗位/主體、動作、範圍、當前版本、過期/拒絕/補充/爭議出口 |
| 持久化 | 模型上下文、checkpoint、業務狀態、審計和待投遞事件的職責；跨庫失敗如何協調 |
| 恢復 / 取消 | 重啟讀取什麼、哪些節點重跑、如何檢查外部副作用；取消執行與取消業務任務區分 |
| 記憶 / 協作 | 用戶/病例/客戶上下文隔離、記憶來源/期限、成員返回結果與失敗語義 |
| 運行結果 | 有效業務產物、引用與覆蓋、失敗/未運行、資源消耗及真實版本 |

有長時人工步驟時，業務狀態和責任記錄不能只存對話或檢查點。圖恢復輸入先通過業務服務驗證主體、對象、動作、期望版本與冪等鍵；只有已保存的有效決定才能推進。事件投遞可能重試，消費者必須能識別同一決定，checkpoint 不提供跨外部系統的原子事務。

先提交、後通知/恢復的間隙要有可恢復記錄；業務提交失敗不能假裝圖已決定成功。若業務狀態與審計由不同組件持久化，明確一致性協議與失敗反饋，不能靠兩個獨立寫入聲稱原子性。

寫後響應丟失是未知結果：先查操作身份及現有記錄再決定重試。模型調用、工具副作用和通知分別決定可重試性；SDK 自動 retry 不自動成為業務可重複調用的證明。

## 最小實現順序

1. 複用當前模型、檢索與服務，固定本次業務路徑和上下游合同，不重建已有效模塊。
2. 依據所選版本建立最小節點/工具與允許狀態轉換；動態選擇僅用於確有需要的局部。不要默認啟用雲追蹤、外部記憶或額外 shell 工具。
3. 實現域內權限、對象版本、冪等與業務狀態源，再接執行暫停/恢復和 UI 事件；模型不持有批准寫入身份。
4. 小範圍驗證真實路徑與故障窗口，只有確需某運行依賴時才準備；安裝/收費/外發沿會話已有授權和憑據規則。
5. 完成狀態/協議兼容與直接受影響舊入口檢查，記錄真實啟動/恢復辦法和產物。運行目錄/依賴/緩存不進普通 Git，責任證據按業務保留。

用戶只要求選型或計劃時，交付上述設計與待驗證條件即可；要求實現時繼續到實際運行結果，別以結構圖代替工程交付。

## 驗證選型和實現的差異

| 情景 | 要觀察的結果 |
| --- | --- |
| 固定兩步只讀任務 | 合理保留普通代碼/已有循環，不為框架引入而擴大系統 |
| 長時審核、進程重啟 | 正確對象與版本恢復；真實待辦仍存在，超時不默認同意 |
| 副作用已發生但 checkpoint/響應尚未保存 | 不重複創建有效業務結果，能對賬未知狀態 |
| 重複/亂序/過期人工回調 | 身份與當前版本校驗成立；拒絕過期，重複返回同一決定 |
| 取消執行嘗試 | 停止允許取消的計算；已提交業務記錄不回滾成未發生，業務終態另受規則約束 |
| 工具/模型錯誤或預算耗盡 | 明確失敗/未完成與可用範圍，不無限重試、不偷偷切外部服務 |
| 多角色成員達到最大輪數或部分失敗 | 檢查真實交付和覆蓋，不將框架 SUCCESS 當目標通過 |
| 多用戶記憶/工具訪問 | 不串用戶/病例/租戶；合法拒絕也被記錄，日誌不復制不必要正文 |
| 協議/圖版本更新 | 舊會話/檢查點不會被新代碼錯誤解釋；顯式遷移或受控停止 |

方案比較固定業務問題、工具和儘量可比的模型/預算，先確認恢復/權限/結果要求，再比較開發維護成本與時延。沒有實際運行就不宣稱可靠性；沒有證據不能對失敗率、吞吐或準確率造數。

Skill 維護可用獨立只讀場景試用：如重複報銷審批、帶暫停的工單、只讀 CLI、跨會話助手、工程批任務。測試請求只提供實際背景和目標，不把預期框架當答案塞進去；諮詢範圍、實現範圍與主觀建議分別審閱。

## 銜接既有工程

已有 RAG 選型作為檢索輸入合同；數據準備繼續負責原值/來源，Agent 編排不自行修造業務事實。按項目現有 Architecture / Feature / Evals 維護，成熟項目不另加一份重複狀態機或並行驗收系統。

交付至少說明：選擇哪層、為什麼、版本/部署約束、實際修改、正常/恢復/拒絕路徑的證據，以及未滿足項。Skill 格式檢查、代理場景試用和真實運行故障測試是不同證據，不能互相替代。
