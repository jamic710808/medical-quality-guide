## 文檔職責

- `docs/PRD.md`：唯一產品級需求事實源，記錄用戶價值、範圍、穩定需求 ID 和 Given/When/Then 驗收。
- `docs/specs/product-spec.md`：唯一項目級總行為合同，記錄跨 Feature 對象、狀態、不變量、共享交互、安全恢復和兼容規則。
- `docs/specs/feature-map.md`：已確認 Feature 邊界、需求/PSC 歸屬、優先級和依賴的唯一事實源。
- `docs/specs/FNNN-<slug>/spec.md`：單個 Feature 的行為、狀態、邊界和驗收。
- `docs/specs/FNNN-<slug>/plan.md`：該 Feature 的實現方案、影響範圍、順序、風險和回退。
- `docs/specs/FNNN-<slug>/tasks.md`：可獨立驗證的任務、依賴、完成證據和驗證方法。
- `docs/architecture/architecture.md`：框架、依賴、數據、服務邊界和技術決策。
- `docs/verification/`：記錄真實命令、退出狀態、可觀察結果和未驗證項。
- `evals/FNNN.json` 與按需創建的 `evals/product.json`：引用已有 AC / PSC 的驗收用例與檢查綁定；業務合同仍以 PRD / Spec 為準。檢查實現放入對應工程的測試目錄。

## 開發規則

- 只實現 Feature Map 中已確認且由當前請求授權的 Feature；保持 PRD、Product Spec、Feature Map、三件套、架構和實現一致。
- 產品範圍或驗收變化時使用 `$product-prd`；跨 Feature 合同變化時使用 `$product-spec`；Feature 邊界或任務變化時使用 `$feature-spec-planning`。
- 使用 `$project-evals` 將本次 AC 具體化為用例，在實際工程中綁定並運行檢查。用例結構通過只證明定義一致；完成驗收需有效行為證據。變更時只更新受影響用例，原始日誌和大報告不默認進入 Git。
- Task 按可獨立驗證的結果拆分，可以跨頁面、服務、數據和測試；不得使用 FE、BE、INT 或 Pack 技術車道標籤。
- 只有完成證據和最窄驗證真實通過後才勾選 Task；按產品範圍、共享行為或局部功能的實際影響更新對應上游文檔。
- 先映射用戶旅程、狀態、前後端合同和可見結果，再修改代碼。
- 首次前端實現前，在已有設計或 Feature Plan 中說明主要對象名稱的來源、頁面主次與列表瀏覽方式、詳情分組，以及主要入口到對象/頁籤和返回的路徑；不按接口模塊堆頁面，不給簡單任務強加頁籤。界面驗收檢查實際操作與目標視口，編譯通過不能代替。
- 正常、加載、空、失敗和成功狀態服從產品實際需要，不用假成功或隱藏 mock 冒充真實結果。
- 每項驗收只使用一個最窄且充分的驗證方法；通過後記錄證據並停止。
- 不讀取、回顯、提交或複製真實憑證；計費調用、外部寫入和部署必須獲得明確授權。
- 保留用戶已有改動，不使用破壞性工作區回滾。

## Definition of Done

- 行為可追蹤到已確認需求 ID 與驗收標準；
- 直接受影響的頁面、API、數據和後臺狀態一致；
- 最窄相關檢查通過，核心旅程得到可觀察結果；
- 本輪受影響的 README、AGENTS、PRD、Product Spec、Feature Map、三件套、架構和驗證證據已同步；
- 未執行項、外部依賴和剩餘風險已如實記錄。
