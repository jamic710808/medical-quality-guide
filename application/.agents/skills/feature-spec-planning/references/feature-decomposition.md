# Feature 通用拆分規則

在新增或調整 Feature Map 時使用。通用化的是判斷方法與檢查標準；具體邊界由項目的需求、共享行為合同、
現有能力與交付目標決定。不要預設功能清單、Feature 數量、行業模板或固定的拆分維度。

## 先選擇拆分主線

以用戶當前希望交付、驗證和迭代什麼為起點，結合實際職責與依賴選擇主線。用戶已明確希望按階段或模塊
逐步驗證時，優先據此提出方案；不因為結果主要供內部消費就改回終端業務功能拆分。

| 主線 | 適用情況 | 邊界依據 |
|---|---|---|
| 業務任務或用戶旅程 | 重點是分批交付使用者能夠完成的工作 | 一項可識別的業務結果及其完整必要流程 |
| 處理階段 | 輸入經過連續加工，每步都有可檢查、可複用的中間產物 | 本階段接收什麼、完成什麼轉換、向下一階段交付什麼 |
| 能力模塊 | 職責穩定，需要分別定位問題、優化或替換內部實現 | 明確的職責、輸入輸出約定、消費方和局部驗收邊界 |

三種主線都可成立。一個 Map 可以組合階段、模塊與業務功能，但同一結果只能有一個主責 Feature，避免
對同一工作重複計入。Feature 是規劃與驗收單元，不強制對應代碼目錄、獨立服務或部署單元。

## 從材料識別交付結果

從 PRD 的用戶旅程與驗收條件中識別：誰在什麼條件下發起、使用哪些輸入、完成什麼結果，以及對象或狀態
如何變化；用 Product Spec 核對共享對象、狀態、不變量和恢復規則。優先複用已有描述，不另建一套需求臺賬。

- 用一句話表達候選結果，例如“使用者完成某項操作，得到某個結果”，或“本模塊接收某類輸入，輸出供某消費方
  使用的產物”。數據、模型、索引、轉換產物等均可成為結果，前提是有真實用途與可判定的完成條件。
- 引用實際存在的 REQ/NFR、AC 與 PSC，區分來源事實、Agent 的拆分建議和影響邊界的待定取捨。
- 一個需求可以跨多個 Feature，一個 Feature 也可以承接多個需求；不把每條需求、每個業務對象機械變成 Feature。
- 架構用於識別職責、輸入輸出和真實依賴。模塊邊界可以成為 Feature 邊界，但不能僅按框架、服務、數據庫或
  模型的數量機械分配。Map 可以先於完整架構細節形成；影響邊界的未定決策要說明，實現選擇留給 Architecture 與 Plan。
- 缺少範圍或全局行為依據時，指出需由 PRD 或 Product Spec 補充的內容，不在拆分中添加新的產品規則。

## 明確獨立驗證與迭代邊界

階段或模塊型候選至少說明以下內容，簡短寫入方案和 Map 正文即可，不另建一套報告或規格體系。

| 內容 | 必須說清的問題 |
|---|---|
| 職責與輸入 | 本階段負責什麼，接收哪些輸入，要求哪些已知條件；哪些工作仍由上下游負責 |
| 輸出與消費方 | 交付什麼產物或能力，哪些信息和狀態必須保留，交給誰使用 |
| 獨立驗收 | 使用什麼代表性輸入檢查輸出，怎樣判斷正確、缺失、失敗或部分完成；不只驗證組件能啟動 |
| 迭代邊界 | 輸入輸出約定不變時，哪些內部處理可單獨優化；什麼變化會影響直接消費方 |
| 依賴與交接 | 依賴的具體產物或能力，以及對接時必須滿足的業務語義和失敗反饋 |

解耦允許有依賴。獨立驗證可以使用固定的代表性樣本，不必等完整應用完成；集成時仍須驗證上下游實際
交接和最終業務結果。若使用依賴替身，說明其邊界，不能把局部通過當成真實鏈路已通過。
只有拆開名稱或目錄、內部仍互讀未約定狀態時，不能宣稱已解耦。

## 形成候選並判斷拆分或合併

圍繞選定主線歸併同一職責所需的步驟，再對邊界有疑問的候選應用下列判斷。無需逐對比較所有候選或計算評分。

| 判斷 | 適用依據與處理方式 |
|---|---|
| 保持為一個 Feature | 相關步驟共同交付一個業務結果，或完成一項有明確消費方的階段/模塊職責；可以涉及一個或多個技術層。 |
| 考慮拆開 | 具有不同職責、可單獨驗證的產物和相對穩定的交接約定，並能分別定位問題或迭代；說明分開的收益及新增依賴。 |
| 考慮合併 | 沒有可用的交付物或局部驗收邊界，改動總要穿透兩邊才能完成同一職責；或必須一起生效才能維持同一操作的不變量。不能只因沒有獨立頁面或終端用戶流程就合併。 |
| 允許有依賴 | 明確前置輸入與輸出約定後能單獨驗收即可；不要求模塊完全孤立運行，按需要保留組合驗收。 |
| 單列能力模塊 | 有實際職責、輸入輸出和明確消費方即可評估，不要求必須被多個 Feature 使用；僅以公共代碼或未來複用為由抽象平臺時，仍需證明實際消費需求與完成條件。 |
| 調整粒度 | 依據職責、結果、驗收與迭代邊界複核；不因模塊有名稱就自動單列，也不按頁面、文件數、預計時長或固定任務數決定。 |

跨 Feature 的長期業務規則可以通過共享 PSC 共同遵守；結合職責、交接和不變量判斷是否合併，
不要因為共享一個對象或狀態就把所有流程合成一個 Feature。實現同一結果所需的空、失敗與恢復路徑通常
隨該結果一起規劃；若異常處理有獨立職責、消費方和結果，再判斷是否單列。

例如：簡單內容發佈中的審核可以屬於發佈 Feature；當審核具有獨立隊列、轉交、退回及單獨驗收目標時，
可成為另一個 Feature。又如媒體導入、轉碼處理和分發交付，各自存在產物、消費方和可驗證約定時，可以按階段拆分。
這些僅用於說明判斷方法，不是其他項目必須套用的功能清單。

## 檢查覆蓋、依賴與首批交付

- 每個 REQ/NFR 與 PSC 至少分配給一個 Feature，每個 Feature 同時引用來源需求與總規格合同；檢查實際業務
  含義是否被承接，不能僅靠列出 ID 證明覆蓋。PRD AC 的結果也應有歸屬，後續由 Feature AC 展開。
  階段只承接某條端到端 AC 的部分條件時，寫明貢獻和組合驗證安排，不宣稱階段完成等於該條 AC 已整體通過。
- 每個結果有明確主責 Feature，其他 Feature 可消費其輸出；共享 PSC 可由多個 Feature 共同承接。
  不把所有 NFR 或 PSC 無差別分配給所有 Feature。
- 依賴要指出所需的業務狀態、數據、能力或輸出。區分必要前置與建議實施順序，不把團隊分工或同用一個服務
  當成 Feature 依賴。依賴不得循環；出現循環時檢查邊界、共享合同或交付順序，不能靠刪掉真實依賴解決。
  開發中的返工反饋不等於循環依賴；可先明確最小輸入輸出約定，再用樣本完善各階段。
- 根據已確認優先級與必要依賴推薦順序，說明首批能驗證的產物、能力或業務結果。階段驗證可先貫通代表性樣本，
  不要求完成全部上游數據或通用平臺才開始下游驗證；同時保留當前結果必需的業務規則與質量要求。
- 模塊內部優化優先驗證該模塊的產物和直接消費方；輸入輸出語義或共享狀態變化時同步受影響合同和組合驗收。
  模塊分別通過後，仍須核對 PRD 的完整業務結果，不能遺漏用戶入口、後續流程或必要的端到端驗證。
- 範圍外、已批准延期與 Agent 建議延期要分清；未批准的延期建議不能成為漏掉當前需求的理由。

## 呈報方案與確認

默認給出一套推薦方案，先說明為何採用該拆分主線。每個候選說明名稱、可驗證結果、範圍、來源合同、依賴和
優先級；階段/模塊補充輸入輸出、消費方、局部驗證與迭代邊界。用一兩句話解釋拆分依據，對明顯邊界不展開長篇
論證；只有真實取捨會改變範圍、驗收或交付順序時，才比較備選方案及其影響。

人工重點確認拆分主線、首批結果、能力能否延期、階段是否需要單獨優化及哪些流程必須一起交付。常規歸類、覆蓋核對和依賴整理
由 Agent 完成，不逐項向用戶索要拆分答案。已有材料足以判斷時直接推薦；只有無法從來源或當前授權解決、
且會實質改變邊界的問題才詢問。

僅討論時直接在對話中呈報，不創建文件。獲准落盤後，把最終理由和順序寫入 Map 正文；若已經討論過，
複用討論結論，不重複生成一份報告。確認與自行決策的授權邊界沿用 SKILL.md；授權只確認 PRD、選擇架構
或生成文檔，不自動等於允許自行決定 Feature 邊界。

完成前檢查：每個候選有明確職責與結果；階段/模塊有輸入輸出、消費方及獨立驗收與迭代邊界；需求和合同無遺漏；
主責明確；依賴可解釋且無環；首批結果與最終組合結果的驗證分清；重大取捨已按授權處理。
文件格式校驗只能驗證結構與追蹤，不能證明邊界合理、模塊已解耦或實現已經通過驗收。
