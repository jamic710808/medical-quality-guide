# 項目驗收與 Evals

把已有驗收合同轉為具體輸入、操作、判定和證據。PRD / Spec 決定業務行為；用例引用它們，項目原生測試執行檢查，驗證記錄保存結果。

## 入口與範圍

- **設計用例**：讀取 PRD、總 Spec、Feature Map 和本次 Feature Spec，生成或增量更新用例；不要求實現、測試命令已經存在。
- **落地與執行**：在用戶授權驗證或開發的範圍內，讀取實際工程和現有測試，綁定或補齊最窄檢查，再執行並記錄結果。
- **變更迴歸**：沿用原用例 ID，只更新受影響的定義、數據和檢查；複用輸入未變的有效證據。
- **只討論方案**：只讀說明，不創建用例或運行目錄。

先確定實際應用根，不能把存放 Skills 和客戶資料的外層目錄當成產品根。讀取適用 AGENTS 和已有驗收入口。首次為本項目採用此格式時，不覆蓋現有測試目錄或報告約定。

本格式承接項目已有的 PRD → PSC → Feature AC 鏈。PRD、總 Spec、Map 的確認關係沿用現有流程；Feature Spec 已明確 AC 就可先設計用例，不要求 Plan/Tasks 已 ready。缺少合同或產品決定時列出具體缺口；不能從當前實現反推預期，再宣稱它符合需求。沒有這條文檔鏈的項目先複用已有驗收，不為了調用本 Skill 補建 PRD。

## 1. 從合同設計用例

讀取 [用例格式與示例](references/eval-format.md)。在實際項目創建 `evals/FNNN.json`；跨 Feature 的總體驗收確有需要時創建 `evals/product.json`。

- 每個 Feature AC 至少由一個用例承接，一個用例也可關聯多個共同驗收的 AC；不按 PRD 段落機械拆用例。
- 來源沿用 AC / PSC 編號，通過上游文檔回溯 REQ/NFR。輸入、前置狀態、動作、預期結果必須足夠具體，能區分正確和錯誤實現。
- AC 只由 PRD 或對應 Feature Spec 定義，PSC 只由總 Spec 定義；輔助資料中的示例或引用不能擴充正式驗收範圍。
- 覆蓋合同要求的正常流程、異常與恢復、共享不變量，以及直接受影響的舊行為。不要擴展成全項目測試矩陣。
- 查看總 Spec 的產品級門檻，明確哪些必須組合多個 Feature 才能證明；把選中的 PSC 放入 product 套件。單個 Feature 通過不代表整條旅程已通過。
- 性能、準確率、次數等門檻來自已確認合同；沒有依據時標明待確定，不能自定 95% 等指標。
- 先檢查已有測試。已能證明同一條件時複用一個檢查；用例之間共享檢查時，檢查必須實際斷言所有關聯用例。
- 尚無真實執行入口時 `check_ref` 為 `null`。這代表設計草案，不代表失敗或已通過；不填假命令。

涉及業務前端時，把已確認旅程和頁面設計具體化為操作檢查，不另造驗收編號或固定頁面模板：

- 取代表性來源對象，核對業務名稱與編號、狀態及適用範圍；確認同一對象在直接關聯入口一致，缺少名稱時未憑代號編造。原始證據仍能回查。
- 從實際鏈接或按鈕進入預期對象與詳情分組，完成操作後看見對應結果，再返回原工作；有頁籤時驗證默認/指定落點及設計承諾的刷新恢復，無頁籤則檢查實際採用的結構。
- 按任務驗看目標視口下的主工作區、關鍵操作、列表定位和比較，不能用文字存在、截圖已保存或 HTTP 200 代替使用體驗。圖等專用視圖只驗證其實際承諾的交互，不把只讀查看當成關係編輯。

以上按本輪範圍選擇並綁定到已有 AC/PSC；不因通用檢查示例給產品新增業務功能。一次瀏覽器操作能同時證明多項時複用該證據；可變數據的預期來自有效合同及本次來源，不把偶然的方案數量寫成永久規則，也不能只把接口當前值複製為全部預期。

運行結構校驗；有多個本次套件時重複傳入 `--suite`：

```sh
python3 <SKILL_DIR>/scripts/validate_evals.py <項目根> --suite evals/F001.json
```

它檢查來源、ID、覆蓋和綁定格式，不判斷預期是否符合客戶意圖，也不執行測試。設計階段由 Agent 對照來源審閱用例含義，新增產品決定回到上游確認；既有合同的具體化不重複索要批准。

## 2. 綁定實際檢查

結合 Architecture、當前源碼與測試入口選擇方法：

- **command**：複用或編寫項目原生測試、接口檢查或瀏覽器行為測試。退出 0 應代表全部關聯斷言已執行且通過；沒有收集到用例、跳過必要檢查或依賴缺失不能返回成功。只構建成功、HTTP 200、文件存在不能替代業務結果。
- **manual**：記錄可重複的操作步驟、預期和應保留的證據；適用於尚無自動化入口的真實體驗核查。由人或當前 Agent 實際操作並審閱，不能用 `echo PASS` 包裝成自動檢查。
- 開放式 AI 輸出可使用項目已有的評分腳本（仍屬 command）或人工 rubric。寫清樣本、評分準則、重複次數和門檻依據；保留模型/提示版本，並通過人工樣本校準評分。沒有實際授權時不調用計費模型或外部寫服務。

測試源碼和輸入樣例放入項目原有測試目錄；根部 `evals/` 只存用例定義。為檢查列出實際實現、測試、數據、配置和必要 lockfile 的 `inputs`，不包含日誌、生成目錄或整個項目根。命令為參數數組，路徑相對於項目根；需要切換目錄時採用工程現有參數或項目測試腳本。

運行 `--require-bound` 檢查來源狀態、全部用例綁定和輸入是否存在。它允許 manual 檢查存在，不意味著人工驗收已發生。規劃階段可以記錄計劃中的檢查，實際實現後、執行前才要求綁定通過。

## 3. 執行、記錄與接回開發流程

讀取 [執行與維護銜接](references/execution.md)。按本次範圍運行綁定檢查；失敗後在已有開發授權內修復並重驗受影響項。單純要求評估時報告失敗，不自動更改產品。不能為了讓代碼通過而刪用例、降低閾值或改寫預期。

- `plan.md` 的驗收映射關聯 eval ID；`tasks.md` 的驗證與完成證據引用實際檢查和結果，不復制一套業務規則。
- 檢查結果區分 `pass`、`fail`、`not_run`、`blocked`；已執行但輸入變化的證據標為 `stale`，基礎設施或命令異常標為 `error`。未通過項不能因“覆蓋了 AC”而算完成。
- 正式結果寫入項目已有驗證記錄（標準工程為 `docs/verification/`），包括用例、版本/輸入、實際命令或操作、斷言結果、證據位置和未驗證項。日誌與大產物先加入忽略規則，不默認提交。
- 更新受影響的 Task 狀態；所有本次必需用例有有效通過證據才算對應驗收完成。跨 Feature 的產品驗收需單獨完成。

## 完成標準

只要求設計時：交付可追溯用例、覆蓋情況和待綁定/待明確項。要求可運行驗收時：交付檢查實現、實際執行結果及證據；結構校驗和業務結果分別報告。純腳本通過不能宣稱整個產品滿足需求，結果只適用於本次覆蓋和運行條件。
