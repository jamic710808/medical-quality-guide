# 準備已確認需求資料

為後續 MVP 和技術架構討論準備原始需求資料入口。默認只創建缺失目錄，並告訴 FDE 對應文件應放在哪裡；不生成需求正文或示例業務材料。

## 目錄結構

先讀取適用的項目指令，確定外層工作目錄：複用用戶指定路徑或當前對話已確定的位置，信息不足時再詢問。`Raw/` 與獨立開發項目同級，不在開發項目內另建第二個原始資料區。用戶已經明確原始資料目錄時使用該位置。

```text
<工作目錄>/
├── Raw/
│   └── confirmed-requirements/
│       ├── customer-requirements/
│       ├── communication-records/
│       └── business-agreements/
└── <開發項目>/
```

目錄統一使用上述英文名；客戶原文件名保持原樣。只補齊三個資料目錄及必要父目錄，已有目錄和文件保持原樣；遇到同用途的既有中文目錄，先說明與新結構的對應關係，不自動改名、遷移或創建重複資料副本。不要求改造 Raw 中其他業務數據的目錄結構。

## 引導 FDE 放入資料

創建後展示實際路徑與目錄樹，並說明三類資料的用途：

| 目錄 | 應放入的文件 |
| --- | --- |
| `customer-requirements/` | 客戶提供或雙方確認的需求說明、業務目標、範圍和驗收約定 |
| `communication-records/` | 與需求相關、已核對的會議紀要、崗位訪談及補充溝通記錄 |
| `business-agreements/` | 雙方確認的業務口徑、處理規則、責任邊界及限制條件 |

提醒 FDE 保留原文件名、內容、日期和已有確認說明。目錄名稱不改變文件中的確認狀態；局部待確認、尚未批准或個人判斷仍保留原樣。不要將未核對的材料自動認定為已確認。

FDE 可以自行放入文件。只有用戶提供來源並要求複製時才執行復制：沿用已明確的類別，保留原件；同名衝突或歸屬不明的文件先列出，不覆蓋、不猜測、不自動拆分正文。同一文件涉及多個方面時保留一個原件位置，不製造三份副本。

## 完成邊界

- 核對三個目錄存在且沒有覆蓋已有文件；列出已創建或複用的路徑。
- 執行過複製時，報告已複製文件及未處理原因；尚未放入文件時如實說明，不宣稱需求已經整理完成。
- 不在本步驟生成規範化文檔、修改 AGENTS.md、確定 MVP 範圍或設計技術架構；後續任務按用戶要求使用這些資料。
