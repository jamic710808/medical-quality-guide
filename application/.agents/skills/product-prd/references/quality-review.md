# PRD 內容質量審閱

在草稿準備確認時使用；更新已有 PRD 時，只審閱變更與直接受影響的依據、目標、旅程和驗收。
依據當前對話與已提供材料判斷，只有影響結論的來源缺失或衝突才回查原文。

## 審閱重點

| 維度 | 判斷內容 | 值得報告的缺口 |
|---|---|---|
| 需求依據 | 關鍵問題、需求與規則能定位到材料條目或用戶指令；來源的確認狀態和適用條件保留 | 把假設寫成事實、衝突未說明、依據超出適用範圍 |
| 目標與取捨 | 重要需求能說明對 GOAL/Journey 的貢獻；全局約束可單獨追溯；優先級反映本輪取捨 | 孤立功能、所有項都標最高優先級卻沒有理由、刪減範圍沒有說明 |
| 成功判定 | 指標有可執行的判定方法；量化目標有基線或補測安排、口徑、數據來源與週期 | “提升效率”沒有判定方式、虛構基線、用功能驗收通過代替業務收益達成 |
| 行為與驗收 | 一項需求表達一個可辨識的業務能力；AC 有真實前置條件、動作和可觀察結果 | “友好/快速/合理”沒有邊界，驗收只複述功能名，規則或旅程相互矛盾 |
| 假設與風險 | 假設顯式標記並關聯 OQ；影響、驗證方法與時機明確；重要未決項未被隱藏 | 待確認規則直接進入已確認範圍、關閉問題沒有結論依據、非阻塞假設沒有驗證安排 |
| 深度與銜接 | 細節足夠支持產品決定；全局與局部規格各有職責；已有設計鏈接標註狀態 | PRD 重複完整狀態機、設計稿被默認視為批准、無關章節為填表而編造內容 |

檢查 GOAL/Journey 引用能否定位到實際條目，REQ/NFR 與 AC 是否表達同一業務含義。腳本只能檢查
結構與非空內容，不能證明來源真實、關聯合理或用戶已經批准。

業務收益例：只有“縮短處理時間”仍不足以判斷成功；應說明計時起止、統計對象、數據來源、觀察
週期和目標。沒有基線則寫補測安排，而不是自行給出一個提升百分比。定性目標也可以充分，例如在
約定試用週期內，由目標角色獨立完成指定任務並記錄是否需要人工協助；任務和週期仍須有用戶依據。

## 如何處理發現

- 僅報告有具體位置和依據的實質缺口，按“位置 → 問題及影響 → 建議修訂/待確認事項”表達。
- 阻塞核心範圍、業務規則或驗收的問題解決前保留 draft；不以所有未知項都清零作為確認條件。
- 非阻塞假設保留 OQ 與驗證安排。來源、目標或條目是否有關聯需要語義判斷，不能只檢查出現了 ID。
- 複用 PRD 的開放問題、決策記錄和當前回覆，不額外生成評分表或審閱報告；用戶要求時再單獨交付。
- 審閱意見是判斷依據，產品決定沿用用戶已有授權；沒有新增決定時不重複請求確認。

## 設計參考

以下資料用於維護本審閱方法，執行 PRD 任務時無需默認聯網或採用其完整流程：

- [Atlassian PRD 實踐](https://www.atlassian.com/agile/product-management/requirements/)：來源、假設和設計鏈接。
- [Aha! PRD 指南](https://www.aha.io/roadmapping/guide/requirements-management/what-is-a-good-product-requirements-document-template)：目標、測量與按項目調整深度。
- [GitHub Spec Kit 模板](https://github.com/github/spec-kit/blob/main/templates/spec-template.md)：優先級理由和可觀察驗收，僅借鑑其 Feature Spec 層面的做法。
- [BMAD PRD 質量審閱](https://github.com/bmad-code-org/BMAD-METHOD/blob/bda3c5929f672019b90f39a3ea27259d35d00974/skills/bmad-prd/assets/prd-validation-checklist.md)：決策充分性、內容實質、範圍和文檔適配。
