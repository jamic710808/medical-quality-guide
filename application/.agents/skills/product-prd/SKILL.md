# 產品級 PRD

把已經收斂的產品決定寫成可由人和 Codex 共同消費的產品合同。只依賴對話、項目證據、Markdown
模板和本 Skill 的輕量校驗器，不依賴 Spec Kit、Superpowers 或其他提示詞框架。

## 輸入與邊界

1. 鎖定唯一目標項目根，讀取適用的 `AGENTS.md`、現有 `docs/PRD.md` 和用戶提供的材料。
2. 先複用當前對話中已經明確的產品決定。只詢問會實質改變用戶、範圍、核心行為、質量底線或驗收的缺口。
3. 沒有足夠事實時保留 `draft`，把未知項寫入“開放問題”；不得替用戶編造目標、指標或業務規則。
4. PRD 只寫 Why 與 What。技術棧、框架、數據庫、目錄、類、協議和部署拓撲寫入 Architecture/Plan。
   外部強制技術約束只有在它會改變產品或合規邊界時才可寫入“依賴與約束”。
5. 一個項目只維護一份產品級 `docs/PRD.md`。不要在總 Spec 或每個 Feature 目錄重複創建 PRD。
6. 背景和需求引用已有材料的路徑/鏈接與條目，或可定位的用戶指令；保留原文的確認狀態和適用條件。
   資料衝突時記錄差異和確認依據，不把推斷或較新的記錄自動當成已批准決定。

## 落盤流程

### 1. 創建或合併草稿

從 `assets/PRD.template.md` 創建 `docs/PRD.md`。目標已存在時保留有效內容和穩定 ID，只補缺失合同，
不整文件覆蓋。狀態先寫 `draft`。

保留模板的章節入口，按當前範圍控制深度。不適用的業務狀態、風險或其他可選內容寫明原因並移除
示例行，不為填表虛構內容。已有原型/設計僅鏈接並標註確認狀態，不要求額外製作。

PRD 至少回答：

- 為什麼做、給誰用、在什麼場景使用；
- 產品目標、成功信號、判斷口徑和反指標；需要量化時寫基線、目標、數據來源和觀察週期；
- P0/P1 核心旅程及可觀察完成結果；
- In-Scope、Out-of-Scope 和優先級；
- 每項需求的觸發、輸入、業務行為、輸出、邊界和恢復；
- 與產品相關、可驗證的性能、安全、隱私、合規及可用性底線；
- 風險、依賴、開放問題和已確認決策。

基線未知時寫明補測方式和時機；簡單工具可用具體的定性判定。功能驗收通過不代表業務目標已經
達成：AC 描述產品行為，業務成效按目標約定的觀察方式在實際使用後判斷。

PRD 只保留影響業務決定的關鍵規則和狀態約束；統一對象、完整跨 Feature 狀態機由 Product Spec
展開，局部流程由 Feature Spec 展開。後續規格引用原有需求，不復制多份可獨立修改的合同。

### 2. 建立穩定追蹤

- 功能需求使用 `REQ-001` 起的三位穩定編號。
- 非功能要求使用 `NFR-001` 起的三位穩定編號。
- 驗收使用 `AC-001` 起的三位穩定編號。
- 每條 AC 寫明來源 REQ/NFR，幷包含獨立的 Given、When、Then。
- 每項需求說明來源與確認依據，關聯已有 GOAL/Journey，並說明優先級理由；全局 NFR 可關聯目標
  或明確的外部約束，無須虛構旅程。來源鏈接直接複用，需求到目標的關聯必須解釋實際貢獻。
- GOAL/Journey 編號保持穩定。更新舊 PRD 時在現有表格或鄰近說明中補關聯，不為了套新模板重編 ID。
- 刪除或替換需求時保留變更記錄；不要回收舊編號給另一個語義。

### 3. 審閱並確認產品合同

確認前讀取 [內容質量審閱](references/quality-review.md)，核對依據、目標關聯、取捨、可驗證性與
文檔深度。只報告有位置、有證據的實質缺口；已有審閱僅複查本輪變更及直接影響的部分。

向用戶集中呈報會改變產品結果的決定：目標用戶、核心旅程、範圍、優先級、質量底線、替代路徑和
仍會阻塞實施的問題。用戶當前指令已經明確覆蓋這些決定時，可把該指令作為確認依據；不要要求特定口令。

只有產品合同已獲確認、沒有阻塞型開放問題且文檔不含模板槽位時，才把 frontmatter 改為：

```yaml
status: confirmed
```

普通待驗證假設可以保留：正文標為假設並引用開放問題，記錄影響、是否阻塞、驗證方式與時機。
開放問題使用“待確認/處理中/已解決/已關閉”（亦識別 open/closed）；已關閉項寫處理結論及依據。
不得僅改狀態繞過阻塞問題，也不把內容審閱意見當成用戶確認。

### 4. 校驗

從實際加載的 `SKILL.md` 定位 `<SKILL_DIR>`，運行：

```bash
python3 "<SKILL_DIR>/scripts/validate_prd.py" "<項目根>" --require-confirmed
```

校驗器檢查狀態、章節、REQ/NFR/AC 唯一性、AC 來源、非空 Given/When/Then 和需求覆蓋；對 confirmed
文檔再檢查需求表必填內容、開放問題狀態與關閉依據、阻塞項和模板殘留。draft 允許保留待填寫的表格。
來源是否充分、目標關聯是否合理、規則有無矛盾由內容審閱判斷；腳本通過不能代替審閱或用戶確認。

## 變更規則

- 下游 Product/Feature Spec 發現新產品行為、範圍或驗收時，先更新 PRD 並重新確認，再調整總 Spec 與 Feature Map。
- 實現細節變化但產品行為不變時，不改 PRD。
- 已有項目只需要按代碼事實補文檔時，不使用本 Skill；按項目已有的文檔維護約定處理。
- PRD 確認後先使用 `$product-spec` 凍結跨 Feature 總合同；總 Spec confirmed 後再使用 `$feature-spec-planning`。

## 完成標準

- `docs/PRD.md` 是唯一產品級需求事實源；
- Why、用戶、旅程、範圍、需求、NFR、驗收、風險與開放問題完整；
- 每個 REQ/NFR 至少被一條 AC 驗收；
- 重要需求的依據、目標關聯和優先級理由可追溯；成功信號有可執行的判斷方式；
- 文檔沒有實現方案汙染、模板槽位或偽造事實；
- 內容審閱發現的實施阻塞已解決，其他假設保留明確的驗證安排；
- 需要進入 Product Spec 與 Feature 拆分時，狀態為 `confirmed` 且校驗通過。
