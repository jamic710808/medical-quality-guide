# 項目交付與接手

讓接手者不讀聊天記錄，也能找到本輪交付範圍、運行和使用方式、驗收依據及剩餘責任。複用項目已有文檔，只補缺失內容；文檔描述當前真實實現，不另建一套產品規格。

## 定位範圍與事實源

先讀取適用 AGENTS、項目入口和用戶指定範圍，確定實際應用根、接收對象及交付版本。外層資料區不是應用工程；已有原型或局部成果按原範圍交付，不自動升級為生產系統。

- 已採用標準工程時，讀取本輪相關的 PRD → Product Spec（PSC）→ Feature Spec / Plan / Tasks、當前代碼、`evals/` 和 `docs/verification/`。
- 其他工程沿用已有需求、測試和文檔入口，不為調用本 Skill 補建整條文檔鏈。
- 業務約定說明應該做什麼，當前代碼說明實現了什麼，運行記錄說明實際驗證了什麼；文件名、Task 勾選或一次構建成功不能替代驗收。
- 用戶只要求設計交付方案時只讀討論；要求整理或更新交付材料時，直接完成本地文檔和清單。外部發送、發佈、部署及簽收按已有授權執行，生成文檔本身不增加這些權限。

先簡述本輪範圍和核查方式。普通目錄與文件名可自行沿用現有約定；僅當缺失信息會改變交付範圍、接收權限或業務結論時詢問，並繼續其餘工作。

## 1. 核對當前成果與驗收依據

讀取 [工作流與證據銜接](references/workflow-and-evidence.md)，建立“範圍條目 → 當前規格 → 實現入口 → 驗收結果/證據 → 交付材料”的對應。沿用原有 ID；跨功能的產品驗收與單個 Feature 結果分別說明。

檢查證據適用的代碼、規格、樣本和環境。複用輸入未變的有效結果；缺失、過期、失敗和未執行保持原狀態。需要補驗時使用項目原生檢查，項目已有 `$project-evals` 時沿用其用例與結果格式。不要為記錄同一結果重複執行檢查。

發現問題按已有授權處理：交付文檔錯誤在本輪修正；代碼缺陷或產品規則衝突回到項目維護流程，已有修復授權時繼續完成相關修復和驗證，否則記錄缺口。不能為了交付而降低驗收條件或把計劃中的功能寫成已實現。

## 2. 整理可接手的材料

讀取 [交付材料規範](references/delivery-documents.md)。默認在實際應用的 `docs/delivery/` 維護交付入口；已有同職責目錄就繼續使用。它是當前交付文檔的維護位置，輸入來自現有工程，版本變化時更新受影響內容，不按日期複製整個項目。

按項目實際情況提供五類內容：交付總覽與清單、驗收報告、部署運行手冊、使用培訓材料、交接記錄。已有 README、運行手冊、測試報告或用戶文檔能回答問題時直接引用並更新，不另外複製同一正文。無數據庫、無模型或不涉及生產運行的項目說明相應項不適用，不補虛構配置。

默認使用簡體中文 Markdown。用戶另有格式要求時採用相應文檔工具，並檢查最終格式；不默認生成 Word、PDF、媒體或 ZIP。範圍內的已知問題、未提供環境、未實施培訓和未發生簽收要具體記錄，不能用空模板佔位後宣稱完成。

## 3. 核對接手方式與文件版本

使用說明中的命令來自項目真實入口。複用已驗證且仍適用的安裝、啟動、操作及恢復記錄；有需要且在授權內時，只補做尚缺的最窄驗證。沒有運行環境時記錄未驗證項和復現步驟，不把文檔已寫好當作換機或生產驗證成功。

讀取 [交付清單與檢查](references/manifest.md)，列出實際要交付的文件和用於核對版本的輸入，生成同目錄 `delivery-manifest.json`。執行 `delivery_manifest.py snapshot` 保存當前字節指紋，再用 `check` 核對清單。腳本只讀顯式列出的文件，不收集整棵目錄、不執行項目命令，也不判定業務通過。

源碼以現有工程或明確版本的源碼包為入口；清單列出的文檔不自動代表全部源碼已打包。只有用戶要求獨立複製或壓縮交付時，按接收範圍組織可運行源碼、必要資產和依賴說明，排除憑證、無關原件、緩存及依賴樹，並核對目標中的相對鏈接和運行入口。內部材料不能隨客戶包自動分發。

## 4. 交回結果

說明交付入口、版本與範圍、實際核查情況、已知限制及下一位接手者需要做什麼。分別報告材料完整性、業務驗收、接手驗證和用戶簽收，不能合併成一個“全部完成”。

已有證據不足時仍交付可用材料，並列明缺項、影響、責任崗位和下一步；不偽造負責人或承諾日期。後續反饋繼續更新同一項目，維護流程修正實現和規格，驗收流程更新受影響結果，本 Skill 同步相應交付說明與清單。

交付範圍內材料已整理、引用及版本檢查通過，且所有未完成事項均如實披露後結束。不要為生成更多文檔擴大功能範圍，也不要把這次材料交付稱為客戶已經驗收。
