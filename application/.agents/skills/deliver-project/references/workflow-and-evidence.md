# 工作流與證據銜接

## 消費現有成果

| 現有成果 | 交付時的用途 | 不應推定的結論 |
|---|---|---|
| PRD、總 Spec、Feature Spec 或同職責文檔 | 範圍、業務條件、AC / PSC、明確排除項 | 規格中出現就等於已經實現 |
| Plan、Tasks、變更記錄 | 定位實現、遺留工作、歷史決定和相關檢查 | 勾選完成就等於實際驗收通過 |
| 代碼、構建配置、鎖文件、接口和遷移 | 確認入口、依賴、運行方式及實現版本 | 有源碼就能在任意環境部署 |
| evals、原生測試及驗證記錄 | 複用用例 ID、預期、實際結果與證據 | 用例覆蓋或結構校驗就等於行為通過 |
| 維護記錄 | 定位本輪已變更文件和真實運行結果 | 一次維護收尾就等於整個系統已驗收 |
| 用戶反饋、培訓和試點記錄 | 採用情況、未決事項、崗位接手和真實效果 | 已發送材料就等於培訓、簽收或產生收益 |

標準工程使用 `docs/verification/` 作為正式驗證結論入口；維護腳本的收據、原生測試日誌和截圖可以被它引用。運行目錄可能被清理：交付仍需要的唯一證據應保存到項目約定的證據存儲，再更新引用；不把臨時絕對路徑作為接收者唯一入口。

已有 `$maintain-project` 負責代碼與有效文檔同步，已有 `$project-evals` 負責用例、執行和驗收記錄。本 Skill 彙總它們的結果，不重建維護狀態機、不替換用例庫、不自動安裝 Hooks。其他工程按相同職責複用原流程，不依賴這兩個 Skill 必須安裝。

## 保留驗收狀態及適用範圍

| 原結果 | 交付報告的處理 |
|---|---|
| `pass` | 引用真實證據與適用版本；只對所覆蓋條目報告通過 |
| `fail` | 保留不滿足的預期、實際結果、影響和整改去向 |
| `not_run` | 說明尚未執行及下一步，不改成“待補截圖但已通過” |
| `blocked` | 寫明缺少的環境、資料或授權及解除條件 |
| `error` | 記錄運行或基礎設施異常，不能當作業務通過或正常失敗 |
| `stale` | 說明哪些輸入已變化；只重驗受影響項 |

複用證據時對照記錄中的代碼版本、未提交改動指紋、規格、測試數據、檢查實現及必要配置。無版本記錄且無法建立對應關係時，標明有效性未確認，不能因文件較新就視為當前結果。生成交付清單的新哈希只能證明現在的文件內容，不能補證過去運行時用的版本。

交付範圍先從用戶要求和有效合同確定，再核對所有範圍條目；不能從“目前通過的用例”反向挑選範圍。局部交付可按用戶限定範圍完成，總體驗收仍有缺口時保持獨立披露。

發現失敗、證據過期或文檔/實現衝突時：

1. 只修正文檔描述即可消除的事實錯誤，直接修正並更新引用。
2. 需要補驗且已有授權時，按項目原生方式執行一次必要檢查，更新原驗證記錄。
3. 需要改代碼或改業務約定時，沿用已有開發/維護授權；沒有授權就記錄問題和處理入口，繼續交付其餘材料。

不得用新報告覆蓋歷史失敗，或把交付說明中的建議寫成已批准的產品規則。

## 材料、接手、簽收分別確認

- **材料狀態**：所需文件存在、內容可用、鏈接和版本可核對；缺項有明確說明。
- **業務驗收**：合同要求的功能和跨功能行為是否有適用的通過證據。
- **接手驗證**：目標角色是否在相應環境完成了運行、操作或恢復任務；只檢查手冊文字時明確為文檔核對。
- **用戶簽收**：誰、何時、對哪個版本和範圍作出什麼確認。沒有記錄就寫未簽收，不預填姓名、日期或默認接受尾項。

企業試點和業務影響依賴真實觀察。報告指標應列基線、統計週期、樣本範圍、口徑、實際結果及限制；只有預估或演示數據時註明尚無真實效果證據。培訓材料可先製作，參加記錄、操作結果和正式交接只能記錄已經發生的事實。
