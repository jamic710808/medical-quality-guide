# 交互式數據分類與整理

幫助用戶通過對話決定“這些資料按什麼業務口徑整理”。工作順序是 **識別數據形態 → 獨立讀取內容 → 推薦業務分類 → 對話修訂 → 審核方案 → 按確認結果構建**。主動讀資料和提出建議，把分類口徑的決定留給用戶。

## 範圍與默認理解

- 使用用戶指定的資料範圍和當前有效的業務背景。已有需求、痛點與功能說明足夠時直接使用；事實不足時再按項目索引回查相關條目，不默認通讀所有背景，也不重新做需求規範化。
- “文件隔離”默認表示每個文件獨立讀取、保留自身來源與處理結果。第一層按 PDF、CSV、TSV、Excel、JSON、郵件、圖片、音視頻等形態識別；第二層依據內容和業務需求歸類。一個業務類別可以包含多個文件及多種形態。
- 現階段只確定類別與文件歸屬，不推斷文件間的業務關係，不連接訂單與庫存等實體，不做跨文件對賬、去重合並、本體或知識圖譜設計。
- API 是獨立的數據來源入口。依據現有接口文檔或用戶提供的響應記錄識別，不把 JSON 文件自動認定為 API。讀取現有材料不包含登錄、調用遠程接口或修改遠程狀態。
- 資料的內容和位置先保持原樣。默認用分類索引引用原始位置；移動、重命名、複製分類副本或生成解析結果，應在具體方案中列明後再執行。不能把“文件隔離”自行解釋為搬動文件。

## 推進方式

### 1. 明確本輪範圍，識別數據形態

範圍已在當前對話給出時直接盤點，不再次詢問已知信息。缺少會影響處理範圍的關鍵信息時，只問清這一點。

列出本輪來源及數據形態；擴展名是初步線索，需要時檢查實際內容。區分本地文件、接口資料和暫不可讀取的來源，給每項分配穩定的清單標識。先彙報簡短的類型分佈，不從文件名直接得出業務分類。

如果用戶只要求盤點類型，到此交付即可，不自動擴展為內容分析或整理執行。

### 2. 逐文件讀取，為討論提供依據

按形態選擇當前環境已有的讀取能力，例如表格字段與記錄、PDF 正文及版面、郵件正文和附件、圖像內容、音視頻時間片段。不要強制所有格式走同一種解析方式。

對每項記錄：讀到了什麼業務內容、讀取到什麼範圍、哪裡仍不清楚。大文件可以先取代表性樣本，但要註明樣讀範圍；業務性質還不清楚時繼續針對性讀取或標為待確認，不以少量樣本冒充全量結論。無法讀取的內容記錄具體限制，不用文件名補猜。

文件內的多種內容可分別記錄讀取結果；拆分成多個產物、改變文件邊界或跨文件合併，需要在後續方案中說清。局部讀取問題不妨礙先討論其他已讀材料。

### 3. 圍繞一個關鍵決定展開對話

把已讀內容放回用戶的業務背景，提出具體可修正的分類建議。不要只問“你希望怎麼分”，也不要一次端出已經替用戶定案的完整分類體系。

每輪按下面的節奏推進：

1. 簡短說明相關材料表達了什麼，並給一兩個可核對的例子。能從材料中查到的事實先自行查，不轉成用戶問卷。
2. 給出推薦的業務類別、納入邊界和理由。存在有意義的替代方案時，再提供兩三個選項及差別；不為湊選項製造無用方案。
3. 默認只問一個當前最關鍵的分類決定。依賴這個回答的問題留到後續；用環境支持的提問交互收取回答，沒有專用工具時在對話中提問。**收到回答前，不自行代答或推進依賴該決定的工作。**可以繼續查閱不依賴該回答的資料。
4. 根據回答簡短複述已經確定的口徑，調整文件歸屬和下一問；用戶更改前面的口徑時，僅回查受影響的部分。已確定的內容不重複追問。

事實、Agent 建議和用戶決定分別表述。發現口徑與已讀材料衝突時，指出具體例子並提出調整建議，不一味附和。用戶說“先放著”時記錄暫緩，不當作同意。

問題圍繞分類粒度、類別邊界、多主題文件如何歸屬、例外和整理方式展開，不延伸成架構評審。足以形成可執行的分類方案後就收斂，不為了走流程持續提問。需要示例時讀 [對話示例](references/dialogue-examples.md)。

### 4. 提交具體方案，等待審核

按 [分類方案與結果格式](references/classification-format.md) 維護一份中文 `classification-plan.md`。有實質進展再更新，記錄當前口徑、已確認決定、待確認事項及必要理由，不記錄整段聊天，也不為每輪對話創建新文件。

供用戶審核的方案必須已經具體可查：本輪來源清單、業務類別定義、逐項歸屬、讀取限制、要生成什麼、輸出到哪裡，以及是否改變原文件。清單較長時在對話中摘要並鏈接完整清單，不能只展示少量示例就申請批量執行。

**用戶要求的是“審核確定後構建”：在具體方案尚未得到確認時，保持在討論與方案階段。**可以讀取資料、核對事實、維護草案，不能提前批量創建分類副本或最終解析產物。提出審核後等待用戶回答；等待時長、沒有反對、只認可某個類別都不等於批准整個方案。

確認按實際語境理解，不要求固定口令。若已展示完整方案，用戶明確同意按該方案整理，即可繼續執行；當前對話已有同範圍授權時直接使用，不再次要求確認。

### 5. 按確認方案構建並核對

執行已確認的類別、文件清單、動作和輸出位置。默認生成按業務類別組織的分類索引，各來源保持獨立並指回原始位置；用戶同時確認瞭解析結果或目錄副本時，再生成這些具體產物。不要順帶搭建通用解析框架、數據庫或數據平臺。

核對來源清單中的每項都有明確結果或未完成原因，業務歸屬符合已確認口徑，索引位置有效；生成解析內容時保留原文含義和不確定性。複製文件時核對源與副本一致，保留原件。

執行中發現影響已確認分類或整理方式的新情況，只將受影響部分帶回討論，其餘已獲確認的獨立工作可繼續。未變的決定不重新審批。

交付分類索引與已生成產物，說明實際覆蓋範圍及未解決項。暫緩或讀取失敗的文件不算整理完成，分類相同也不表示已經建立業務關係。

## 存儲與已有技能

- 用戶指定路徑優先。默認將本輪方案與分類結果放在 `docs/04_classify-project-data/`；已有同用途目錄時沿用，來源與輸出分開，避免再次將輸出當作輸入。
- 本技能處理業務數據的分類討論與整理。需求資料規範化繼續由 `normalize-project-requirements` 承擔；痛點與功能看板繼續由 `review-project-requirements` 承擔，保留它們原有入口和資源。
- 本技能可獨立使用。交互方式參考 Superpowers 的 [brainstorming](https://github.com/obra/superpowers/blob/main/skills/brainstorming/SKILL.md) 與 Matt Pocock 的 [grilling](https://github.com/mattpocock/skills/blob/main/skills/productivity/grilling/SKILL.md)（`grill-me` 當前調用的交互邏輯），吸收查明事實、帶建議討論、按回答推進和確認後執行的思路，不依賴安裝或運行它們。
