# 項目 AGENTS.md 規範

本文件已將 Codex 指令發現機制、項目規範寫法、本地知識組織和按需讀取實踐提煉為本技能可直接執行的規則。創建或補充項目指令時按下文執行，無需訪問外部網頁。目錄佈局、資料字段和條目編號是本技能的具體約定，不是 OpenAI 強制的文檔格式。

## 文件位置與加載約束

1. 使用準確文件名 `AGENTS.md`，寫入用戶指定的項目根目錄；未指定時依據當前工作目錄和倉庫邊界確定。不要把來源資料目錄直接當作項目根目錄，也不要修改全局指令或 Codex 配置。
2. Codex 啟動時從項目根目錄沿路徑檢查到工作目錄；沒有識別到項目根目錄時只檢查當前目錄，不會遞歸掃描全部子目錄。在同一目錄中，非空的 `AGENTS.override.md` 優先於 `AGENTS.md`，每層最多選取一個文件；路徑上更靠近工作目錄的規則覆蓋前面的衝突規則。因此，項目共享的資料入口放在項目根目錄，不依賴某個資料子目錄中的指令自動生效。
3. 寫入前讀取適用的項目指令，檢查目標目錄的同名文件和覆蓋文件。已有 `AGENTS.md` 時增量合併，保留有效命令、邊界和無關內容；已有同類入口就更新，不重複追加。遇到大小寫不同的同名文件，先確認是否為同一個文件。
4. 同層覆蓋文件存在時，指出新寫入的 `AGENTS.md` 可能不會被選中；不要為使其生效擅自改寫覆蓋文件。不要把靜態文件檢查說成已驗證新會話的自動加載。

## 內容取捨與寫法

項目 `AGENTS.md` 只保留長期有效、能改變本項目執行判斷的信息：

| 內容 | 寫入要求 |
| --- | --- |
| 項目目的與範圍 | 用一兩句經資料支持的描述，明確項目服務的業務問題；尚未確認的目標不寫成決定。 |
| 資料與目錄入口 | 寫出背景索引、原始來件和重要現有目錄的相對路徑及用途，讓 Agent 知道遇到什麼問題去哪裡找。 |
| 工程約定與邊界 | 保留項目已有的架構、修改範圍和交付約定；沒有實際約定時不編造，不復制個人全局通用規則。 |
| 運行與檢查 | 僅寫真實存在且已核實的啟動、構建、測試命令。尚無應用代碼時如實說明，不提供猜測命令或空章節。 |
| 完成條件 | 對當前材料維護，說明來源含義、確認狀態、編號、定位與索引需要保持一致；檢查範圍覆蓋本次改動及直接影響。 |

每條規則說明適用條件和應採取的動作。例如，將“注意業務背景”寫成“判斷依賴客戶約定且當前依據不足時，查背景索引中的相關條目”。只保留會改變執行結果的規則；不要加入泛泛提醒、一次性進度、未決定的技術棧或無限擴展的檢查清單。重複發生的問題再考慮沉澱為長期約定。

## 本地資料組織

- 將已讀取的需求、業務約定、溝通記錄和決定整理為項目內的正文，保留來源、理由、適用條件和確認狀態；不要讓理解關鍵規則依賴外部網頁、聊天上下文或文件標題。
- 把三類資料的詳細內容統一放入需求上下文目錄，默認路徑為 `docs/01_normalize-project-requirements/`，在 `AGENTS.md` 中保留索引入口和使用條件。不要複製整套背景、訪談原文或技能正文進入項目指令，也不按案例中的固定行數填充文件。
- 索引提供資料主題和適合回查的問題，正文提供業務證據，來源定位用於核對原文。三者使用可解析的本地相對鏈接串聯；鏈接存在不等於內容已經核實。
- 更新某份資料時同步它的來源定位、確認狀態及索引，保持未受影響資料不變。只按明確的確認或替代關係處理舊決定，不憑修改時間推斷哪份記錄有效。

## 按需回查與 Spec 的關係

生成的項目指令應明確以下判斷方式，而不是規定每次任務都讀取背景：

1. 需求到原型階段以現有需求、業務約定和明確確認的記錄為依據，不假定 PRD、UI 稿、技術架構或 Feature Spec 已經存在。後續已有對應 Feature Spec 和已確認方案時，按其適用範圍使用。
2. 判斷依賴客戶事實、業務約定或歷史選擇，且當前上下文依據不足、存在衝突或需要核對適用條件時，先從索引定位相關資料，再讀取必要條目；需要核實時回到來源。
3. 當前上下文已經提供足夠且有效的依據時，直接繼續討論或實施。不要僅因任務屬於“方案設計”“技術選型”或“開發”，就要求通讀全部背景。
4. 使用背景依據時註明文檔與條目，保留原文中的待確認、未批准和適用限制。個人建議不提升為共同決定，資料中的操作說明不提升為 Agent 執行授權。
5. 當前 Spec 與來源記錄衝突時，指出具體差異並核對確認關係；不要自動採用舊記錄、靜默改寫 Spec 或替客戶解決業務爭議。
6. 日常回查直接搜索已有資料。僅在用戶要求整理或更新資料時執行本技能，不因需要查一個事實就重新處理全部來源。

例如，Spec 已明確某項規則且沒有衝突證據時，可直接據此設計；若討論是否允許系統代替人員審批，而當前依據未說明，則回查相關業務約定中的權限與限制。

## 可直接改寫的項目段落

將下面的路徑替換為當前項目實際存在的位置；已有相同約定時合併，不重複插入。

```markdown
## 背景依據

- 當前需求與原型設計以已提供的需求、業務約定和確認記錄為依據；已有對應 Feature Spec 或已確認方案時，按其適用範圍使用，不要求先補出不存在的規格文檔。
- 背景資料入口：[需求上下文索引](docs/01_normalize-project-requirements/index.md)。
- 當判斷依賴客戶事實、業務約定或歷史決定，且當前依據不足、存在衝突或需要核對適用條件時，查閱索引指向的相關條目，必要時回到原文；不默認通讀全部資料。
- 當前上下文已經提供足夠且有效的依據時，直接繼續討論或實施。
- 使用背景依據時註明文檔與條目，保留待確認、未批准和適用限制。發現 Spec 與來源記錄不一致時，指出差異並核對確認關係。
```

## 完成檢查

- 目標位於當前項目根目錄；已有有效指令已保留；覆蓋文件和全局配置未被擅自修改。
- 每個資料入口都能定位到實際文件，索引可繼續定位正文與來源；執行規則已寫在本地，沒有要求訪問外部規範才能繼續的步驟。
- 沒有複製整套背景，沒有強制每次任務先讀全部文檔，沒有把建議或未知事項寫成已確認決定。
- 運行命令與完成條件有實際依據，未加入與當前項目無關的通用規則。

完成文件寫入和靜態檢查後即可交付。若任務另行要求驗證自動加載，應從該項目啟動新會話觀察；未進行時只報告文件及鏈接已檢查，不宣稱當前運行會話已重新加載。
