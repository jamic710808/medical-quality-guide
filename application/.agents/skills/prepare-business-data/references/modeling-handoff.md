# 向檢索與知識建模交接

## 交接的內容

預處理統一的是證據載體，知識建模另行決定對象、關係、語義和工作負載。

| 交接內容 | 後續用途 | 邊界 |
| --- | --- | --- |
| 數據結構/字典 | 理解表、字段、原生類型、聲明的鍵及值域；建立可查詢映射 | 數據庫未聲明的關係保持未知；列名相同不等於同一概念或外鍵 |
| 原文與結構化證據 | 從業務對象/屬性回到來源與位置 | 原值與規範化值分開；只消費允許且覆蓋明確的範圍 |
| 術語/規則參考 | 形成術語、規則及適用性的候選 | 同義詞表和層級是來源主張，不自動成為全球等價關係或已批准規則 |
| 可選候選事實/關係 | 供後續結合原文與業務上下文審閱 | 保留抽取/推斷性質、引用與缺口，不寫成專家確認 |
| 圖像/波形附件 | 提供業務對象與原生資產、報告的有據關聯 | 元數據/附件關聯不等於醫學圖像或信號解釋 |
| 來源與讀取說明 | 讓建模工具知道如何在允許範圍回查、查詢或取片段 | 不復制憑據，不要求將整個大庫塞入提示詞或圖譜 |
| 來源角色/數據分工 | 明確建設、驗證、留出與參考答案的訪問範圍 | 模型構造輸入與評測輸入物理或邏輯隔離，不能把答案混入知識 |

建議交接中列明每個來源/對象種類、訪問路徑、選擇的讀取器、可用與不可用範圍、直接消費方式、來源角色、變換及未解語義；一次實際交接維護一份說明，不重複製作多套“統一知識庫”。

## 共同對象不意味著同一業務實體

EvidenceItem 的 id 是證據對象身份，source.id/version 是來源身份。患者、就診、規則或機構的業務身份需要原始標識及可核查關係；不同來源相同編號、日期接近或文本相似只能成為關聯候選。

統一證據還不是圖數據庫的節點/邊、FHIR 資源或某個本體框架的發佈格式。模型化映射由下階段根據任務與業務語義決定，保留 evidence id 與 locator 回鏈，不能將整個 JSON 直接冒充最終本體。

## 使用現有本體 Skills 時

若項目選擇同級 build-ontology / evolve-ontology，交接前按實際模式核對其 [數據邊界](../../build-ontology/references/ontology-layer-data-boundary.md)與[項目上下文](../../build-ontology/references/project-context.md)：

- 建設模式由項目/本體流程選擇，不因為預處理結束就自動選擇 fixed_split 或 rolling_trajectory。
- builder/evolver 不讀取 reference_label、validation、heldout 的正文或隱藏反饋來設計模型；交接清單隻登記必要的邊界元信息。
- 當前例子中的數據標註可以登記給 Evaluator，但不能併入 builder 的業務證據輸入。
- 不在預處理階段創建或修改 .evoontology/project.json、候選本體、分割比例或 MCP 配置；也不把本地數據轉換視為知識發佈授權。

未採用該本體工具時沿用其項目真實的建模輸入約定，不強制安裝 EvoOntology；通用證據契約和來源隔離仍成立。

## 按消費目標交接三種視圖

同一證據底座可以形成不同消費者視圖，不要求預處理一次生成全部視圖。用戶只要求方案時說明結構與接受條件即可，不因此建索引、建庫或發佈本體。

| 消費者 | 需要的結構 | 准入與限制 |
| --- | --- | --- |
| 結構化查詢/計算 | 原值＋顯式類型/單位/時間解釋、表/字段映射、真實粒度/鍵、範圍與完整性 | 精確計數/缺失判斷需要聲明集合；top-k、未知 JOIN、缺失填 0 不可替代 |
| RAG | chunk/parent/section、原文與檢索文本版本、evidence_refs/locator、分塊/分詞/模型版本、來源角色/用途和質量範圍 | 當前資格/授權先行；原文回放、必要上下文和截斷可見；不能把解析成功的全部材料放同一知識庫 |
| 本體/語義層建設 | 工作負載、結構/術語映射、關係/約束候選、證據支持、範圍/版本及未解問題 | 適配目標系統 Schema；候選不直接發佈，檢索近鄰不代表等價，實例與概念分別處理 |

共同清單沿用項目 manifest 或等價合同：輸入 source/version、對象/分片與摘要、轉換/Schema 版本、允許目的/範圍、角色/授權引用、覆蓋單位/已知總數、缺口/拒絕理由、依賴和回查方法。變換與質量記錄可為 sidecar/關聯表，不任意擴展 EvidenceItem 頂層，不另建第二套證據身份。

## 消費端不能只看 success

| 上游結果 | 正確交接 |
| --- | --- |
| 解析成功、用途/權限未明確 | 不自動授予訪問；限制相應消費並記錄缺項 |
| 參考規則成功讀取、尚未專業審核 | 可在允許研究/候選範圍查看，不能當生產執行規則 |
| 部分解析成功且定位/可用範圍明確 | 僅交付該範圍；依賴完整文書/集合的判斷仍受限 |
| 技術可讀、業務身份/單位/關係未知 | 原文可在授權範圍查看；相關聚合/關係/專業判斷保留未知 |
| reference_label / validation / heldout | 正文只交獲准評測方，不作為索引/本體構造輸入 |
| 新舊版本或撤權/失效衝突 | 消費當前獲准且兼容版本；歷史存在不代表當前允許使用 |

缺失原因、原始值、規範化值和模型解釋分開；質量發現不是自動成立的業務違規。臨床等專業資格由項目對應流程負責，預處理不能生成專家確認。

## 檢索視圖的非破壞性要求

按原生層級/條款/段落/表格分塊，必要時再按目標 tokenizer 拆分；保留主體、否定、單位、表頭和條件。新增標題/表頭作為檢索上下文單獨說明，文字座標回到原始 evidence。摘要/翻譯單列派生身份，不能替換原文。

片段、父文書回取、向量/詞法索引、緩存和聚合均繼承當前範圍；父塊擴展不能跨越片段權限。結構化源無需逐行全文向量化；跨來源同文本可做展示去冗餘但來源/業務身份仍保留。任何未覆蓋/截斷不能變成“不存在”。

## 本體適配與版本失效

使用 build-ontology 時，其 Term / Mapping / Relation / Constraint / Evidence 是目標 Schema；項目 EvidenceItem 與本體 Evidence 不因同名就相同。Relation 只用目標系統允許的類型；術語近似、上下位、等價與個體同一分開，不能直接複製 SSSOM 或任意 RDF 字段冒充該格式。

治理審核/候選狀態可在交接附屬記錄維護，不隨意給目標固定 Schema 加字段，也不往語義自由文本塞 SQL 模板、流程步驟或隱藏答案。沒有明確選擇 RDF 時無需增加 SHACL/OWL 運行依賴。

來源、清洗、語義映射和分塊各自版本化，記錄依賴以便更新/撤回。先限制失效數據消費，再清理索引/緩存；舊版回退不能恢復已撤權材料。源內容、必要責任歷史與可重建派生物分別按項目生命週期管理，不能以重建為由刪除原始業務記錄。

治理細節按需讀取 [數據治理與非破壞性清洗](data-governance.md)；這裡只定義消費者交接，不重做整套清洗工作流。
