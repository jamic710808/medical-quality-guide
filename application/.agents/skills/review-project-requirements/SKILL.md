# 客戶痛點與功能看板

使用本技能處理“根據這些文檔生成看板”“梳理客戶痛點和要做的功能”“說明功能能達到什麼效果”等請求。默認填充用戶已確認的淺色三列模板，讓人直接讀懂 **客戶痛點 → 對應功能 → 預期效果**。全部關聯直接展示，不需要先切換視圖或打開詳情。

這是需求到原型流程的 **02 需求看板階段**：讀取 01 階段需求資料或用戶指定文檔，向後續原型設計提供痛點、擬做功能和預期效果。本技能不創建 03 設計記錄或 04 前端工程，也不把看板內容自動視為甲方已確認。

看板用於說明要解決的問題，不直接決定未來系統的菜單、頁面和操作步驟。後續原型應結合用戶希望呈現的方式，編排未來使用場景；不要把每一行機械轉換成一個後臺模塊，也不要把本看板的版式當作業務系統的 UI 模板。

## 先提煉業務內容

1. **讀取相關文檔**：以用戶指定的資料為準。有規範化索引時先定位相關條目，本項目默認入口為 `docs/01_normalize-project-requirements/index.md`。沒有索引時直接讀取指定文檔，不強制先重跑資料整理。客戶需求說明訴求，溝通記錄補充實際困難，業務約定限定功能的適用條件。
2. **先列痛點**：寫客戶當前遇到的具體困難及影響，例如“事情交出去了，結果跟不住”。痛點應有文檔依據，不把功能名、技術選型或個人設想寫成客戶痛點。
3. **關聯功能與效果**：為每項痛點說明接下來做什麼功能、包含哪些主要動作，以及預期改善什麼業務結果。功能回答“系統做什麼”，效果回答“客戶因此能看清、判斷或完成什麼”。一行表達一組清楚的對應關係；按實際內容決定條目數，不湊固定五條，也不強制痛點與功能嚴格一對一。
4. **核對表述**：原文未規定的準確率、響應時間、節省比例、日期和責任人不能編造。新增建議、待確認條件和預期效果不能寫成已批准決定或已實現成果。對功能有實際影響的業務邊界，簡要寫入對應行或頁腳。

## 默認頁面與生成方式

- 先讀取 [三列看板模板](assets/board.html) 和 [看板數據格式](references/board-data.md)，基於模板填充內容。頁面採用用戶於 2026-09-29 確認的復刻版式：暖白底色、紅／綠／藍三列、圓角卡片、編號與圖標、頂部玻璃卡片和綠植裝飾。左列列舉客戶痛點，中列說明擬做功能，右列說明預期效果。
- 默認保持標題區、範圍標籤、閱讀設置、三列列頭和逐行關聯結構。業務內容寫入數據，複用 [行模板](assets/board-row.html) 與 [裝飾素材](assets/illustrations/)；不要把模板僅當作靈感重新設計，也不要嵌入整張參考截圖。桌面顯示三列，窄屏按每組“痛點、功能、效果”縱向閱讀。
- **允許隨內容調整**：客戶名稱、範圍標籤、需求行數、每行動作數，以及容納內容所需的卡片高度和換行。行數不固定為參考圖中的四行，不裁掉長文或省略業務邊界來湊版式。只有用戶提出新視覺要求時才調整相應樣式。
- 默認包含字號、行距與留白調節及恢復默認按鈕，由 [閱讀控件](assets/reading-controls.html) 提供。`reading_controls` 缺省或為 `true` 時啟用；用戶明確需要無控件的靜態版本時設為 `false`。
- 默認不加入文件清單、來源關係圖、評論、審閱狀態、篩選、視圖切換、導出或“複製提示詞”。不要因為另一個模板包含這些功能而自動帶入；只有用戶明確需要時才增補。
- 來源文件、條目或頁碼保留在項目數據中，用於生成時核對；頁面不顯示技術編號或文件追溯入口。看板描述客戶未來要用的“資料查詢”功能，與看板自身增加文件瀏覽器是兩件事。
- 按數據格式寫入 `board-data.json`。客戶名稱、具體痛點、業務規則及來源路徑放在項目數據中，不能固化到技能、生成腳本或模板。
- 新建時固定使用 `docs/02_requirement-playground/board-data.json` 和 `index.html`，都相對於容納需求資料的工作區根目錄。已有用戶認可的頁面或項目明確入口時，在原位置更新；不因採用新版編號約定另外生成一份同用途頁面。用戶要求遷移時，同步來源路徑、頁面入口和項目指令，不留下兩份當前版本。

新建看板的生成命令（已有頁面時替換為其實際路徑）：

```bash
python3 .agents/skills/review-project-requirements/scripts/build_board.py \
  --input docs/02_requirement-playground/board-data.json \
  --output docs/02_requirement-playground/index.html
```

腳本只讀取數據中明確列出的來源，檢查文件校驗值，並將提煉結果填入模板。它不自動理解文檔；內容取捨、關聯是否成立及來源定位必須先由 Agent 核對。源文檔變更時先複核相關內容，再更新數據中的校驗值。HTML 為可再生輸出，項目數據和模板是生成依據；不要只改輸出 HTML 而使下次生成丟失修改。圖標與綠植來自已確認參考圖的獨立裁片，生成器將其內嵌，輸出不依賴原圖或外部資源。

## 驗證與交付

- 檢查每行三者是否對應：功能確實針對所述痛點，效果說明業務改善，不只是重複功能名稱；來源支持關鍵判斷，未知事項仍明確。
- 用腳本實際生成頁面，核對行數、業務文字和邊界完整，內嵌素材、CSS、JS 可離線使用。檢查閱讀調節及恢復默認行為。
- 按當前會話允許的方式對照模板檢查標題區、三列層級、配色、留白和窄屏閱讀。允許瀏覽器驗證時優先使用內置 Browser（`iab`）；用戶要求自行驗看或禁止自動化時，交付實際預覽入口並如實說明未做自動視覺驗證，不繞過限制。需要在線預覽時啟動本地靜態服務。
- 給出頁面入口及必要的待確認說明，不把生成看板說成業務功能已實現。保留原始文檔和無關技能，不改寫業務確認狀態。

## 用戶明確需要詳細審閱時

只有用戶另行要求文件追溯、需求與約定關係、評論或意見導出等詳細審閱能力時，才讀取 [詳細審閱數據與交互](references/review-data.md)，使用已有的 `scripts/build_panel.py` 與 `assets/panel.html`。這些資源繼續保留，不作為普通“生成看板”請求的默認流程。

`playground` 的六個通用模板獨立保留。由 `$playground` 轉入本流程時仍以本技能的三列模板和生成器為準，不疊加通用 playground 的提示詞輸出、預設或審閱工作流。
