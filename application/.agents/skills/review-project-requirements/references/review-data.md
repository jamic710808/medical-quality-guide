# 詳細審閱數據與交互

僅在用戶明確要求文件追溯、關係瀏覽、評論或意見導出時使用本流程。普通“基於文檔生成看板”請求按 `SKILL.md` 的三列看板流程執行，不加載本流程的交互要求。

本文件定義 HTML 生成器的輸入，字段名是技術接口，字段值和界面使用中文。每個項目僅維護一份 `review-data.json`，不要創建同內容的中英文副本。

## 數據結構

- `schema_version`：當前為 `1`。
- `project`：`id` 為穩定的項目標識；`title`、`subtitle`、`summary`、`scope` 為有來源的中文說明；`as_of` 為資料截止日期；`review_note` 說明需要人工確認的邊界。
- `sources`：明確列出的規範化文檔，每項包含 `id`、相對於本 JSON 的 `path`、該 Markdown 當前內容的 `sha256`。不得把整個原始交付目錄作為輸入。
- `items`：審閱事項列表，格式見下表。
- `relationships`：需求與其他事項的顯式關聯，格式及判斷要求見“需求關聯”。

| 字段 | 含義 |
| --- | --- |
| `id` | 穩定且唯一的面板事項編號；不是新業務單號 |
| `category` | `requirements` 客戶需求、`agreements` 業務約定、`communications` 溝通進展、`materials` 資料現狀、`questions` 待確認事項 |
| `title` / `summary` | 名稱與簡短摘要 |
| `origin` | `原文明確`、`依據記錄歸納` 或 `整理建議，待確認` |
| `fields` | 若干 `{label, value}`，按事項性質取捨說明，不強制填空模板 |
| `references` | 來源條目編號數組，例如 `REQ-001-02`，必須真實存在 |
| `date` | 可選；溝通發生日或明確標註的補充日，不能用文件修改時間代替 |

規範化 Markdown 使用 YAML frontmatter 的 `id`、`type`、`source_date` 和首個一級標題；條目標題為 `## 穩定編號 標題`。生成器兼容這些簡單標量，不負責通用 YAML 轉換。

## 內容編排

- **客戶需求**：展示客戶訴求、擬提供能力、完成標準、適用範圍與關聯約定。明確的原話可直接引用；從多個段落提煉的功能表述標為歸納，新增建議標為待確認。沒有量化指標就展示待量化，不能填寫虛構準確率、響應時長或開發完成率。
- **業務約定**：保留適用對象、條件、審批責任、例外和有效範圍。案例報價與預計時間不自動變成普遍規則。
- **溝通進展**：按原始訪談時間和補充時間分別列項，說明溝通內容、明確的共識或崗位意見，以及還需核對的事項。“有記錄”不等於“已全部對齊”。沒有下次溝通時間就不編排日期。
- **資料現狀**：只描述需求與訪談中提及的系統、資料類型、分佈、更新節奏和缺口，註明是記錄所述。不得以本面板生成過程為由進行數據盤點或連接系統驗證。
- **待確認事項**：說明待確認問題、確認後的用途、原文是否指定負責人。建議向誰核對必須標“建議”，不自動分派任務。

同一約定可被多個功能引用，不需要複製為多份約定。資料與溝通多少由來源決定，不預設數量。

## 需求關聯

每條關聯包含：

| 字段 | 含義 |
| --- | --- |
| `requirement` | 起點，必須是 `requirements` 分類的事項編號 |
| `target` | 終點，必須是已存在的約定、溝通、資料現狀或待確認事項編號 |
| `reason` | 這項內容為什麼與該需求有關，尤其說明約定限制了什麼行為或條件 |
| `references` | 支持這項關聯的來源條目，必須覆蓋起點和終點各自的依據 |

按業務含義判斷關係。兩項內容引用同一文件、同一通用段落或相似詞彙，不足以證明關係。不要把所有約定無差別連到所有需求，也不要從某段訪談存在推斷整場溝通已經完成對齊。

需求的對應文件從其直接來源與顯式關聯的證據條目歸集，顯示真實文件名，並能查看與這條需求有關的條目。共用文件或約定可以反向關聯多個需求；缺少關聯要標為待建立，不自動解釋成沒有約束。

關聯視圖以當前需求為持續上下文。打開關聯的約定、溝通或來源後，仍能返回原需求；主動選擇另一條關聯需求時才切換。原有分類列表繼續提供另一種瀏覽方式，並能返回需求關聯頁。

## 審閱結果

頁面為每個事項記錄 `status`、`comment`、`updated_at`，並關聯項目和資料版本。此信息屬於人工審閱意見，不能修改原始 `origin` 或把來源中的“未批准”改為“已批准”。

導出的 Markdown 供人閱讀或交給 Agent 修訂；JSON 保留項目、版本、事項編號、對應文件、相關需求、關聯約定及理由、審閱狀態、評論和記錄時間。僅納入實際產生的審閱意見及其關聯上下文。複製修訂意見應說明修改目標、依據和人工意見，不直接執行業務動作。

`revision` 根據來源與審閱事項內容計算，`relationship_revision` 根據關聯整理計算。只修改關聯或佈局時不清空原有事項的評論；舊的事項確認不表示新增關係也已經被確認。

瀏覽器本機保存是單人使用方式。頁面可通過 HTTP 分享，但不同人的審閱結果不會自動合併；需要共享保存時應單獨設計，不宣稱靜態 HTML 已支持多人協同。

## 生成與檢查

新建詳細審閱面板時放在 02 階段目錄，使用獨立的 `review.html`，不覆蓋默認看板 `index.html`。已有項目按其實際詳細審閱入口執行，不因下方示例搬遷舊頁面。

```bash
python3 .agents/skills/review-project-requirements/scripts/build_panel.py \
  --input docs/02_requirement-playground/review-data.json \
  --output docs/02_requirement-playground/review.html
```

來源變化後先複核內容和關聯，再更新數據。實際打開頁面，檢查需求與文件、約定的關係、上下文內查看及反向定位，以及搜索、分類、審閱保存和導出路徑。驗證後清除測試評論。已有詳細審閱入口、數據和意見不因默認看板流程改變而刪除。
