# 已有項目持續維護

把本輪變更落實到**現有實現、當前有效文檔和驗證記錄**。業務規則、技術棧、目錄和檢查方法來自當前項目；原型與正式應用沿用同一維護主線，按實際影響選擇需要更新的文件。

配置 AGENTS 與 Hooks 是可選的項目接入工作。Skill 指導 Agent 判斷和執行變更；配套腳本核對文件與檢查證據；Hook 在宿主的指定時點調用腳本。使用 Skill 不等於已安裝或啟用 Hook。

## 選擇本輪入口

- **提出新需求、修復問題或調整已有實現**：執行下方“迭代已有項目”。即使還沒有接入 Hooks，也完成已授權的修改與驗證，不把配置工作當前置條件。
- **要求建立或調整維護機制**：讀取 [項目接入](references/project-integration.md)，維護本項目的 AGENTS、文檔入口和 Hooks。已有項目的實際新需求同時存在時，接入後繼續完成需求。
- **只討論方案**：只讀檢查並說明建議，不改項目或配置。

本 Skill 與項目構建、原型生成等既有 Skills 並列維護。需要某項既有規範時按需讀取，沿用其有效合同；不通過修改那些 Skills 來安裝本工作流，也不依賴它們全部已安裝。

## 迭代已有項目

### 1. 定位同一個項目

讀取有效的項目指令、當前實現入口，以及和需求直接相關的設計或規格。分清外層工作區與應用源碼目錄；按已有入口定位，不憑日期、最新修改時間或默認編號選工程。

先說明本輪要改變的可觀察行為、直接受影響的舊路徑和最窄驗收方法。對已經明確的需求繼續執行，僅澄清會改變業務含義或權限且無法由現有依據解決的問題。

按職責識別已有的需求或設計依據、源碼、使用說明與驗證記錄，不按文件名或階段編號推定項目結構。具體場景的適配示例見 [變更與文件維護](references/change-maintenance.md)。

涉及前端頁面、業務命名或導航時，先核對本輪主要對象名稱的來源和用戶任務，再梳理“入口 → 對象/頁面/頁籤 → 操作結果 → 返回”。有業務名稱時不只顯示內部代號；缺失名稱不猜寫，業務編號與原件保留。不要只改一個標題而遺漏直接關聯的列表、詳情、選擇器或結果；詳情按任務選擇頁籤/分欄，簡單操作不強拆。使用既有設計記錄；同級原型 Skill 可用時按需讀取其 [應用產品設計方法](../build-frontend-prototype/references/product-design.md)，只複用相關設計方法，不另建原型或擴大為全站改版。

### 2. 判斷哪些文件需要跟著變

讀取 [變更與文件維護](references/change-maintenance.md)。建立本輪的小範圍對應關係：**需求 → 受影響實現 → 要更新的當前文檔 → 驗證方法**。對看似相關但無需修改的文件，記錄具體原因。

- 按產品範圍、共享行為、局部功能或實現調整，找到承載受影響約定的現有文件；使用方式變化時同步已有使用說明。
- 原型沿用設計與驗看記錄；正式項目已有 PRD、Spec 或功能文檔時沿用其歸屬關係。文件名稱和數量由當前項目決定，不因調用本 Skill 補建完整文檔鏈。
- 修改文檔正文中的當前描述，避免只在末尾追加“已完成”而保留相互矛盾的舊規則。
- 原始來件和客戶歷史記錄保持原文。新需求註明本輪來源和適用範圍，不偽造客戶批准。

項目已有 `evals/` 或用戶要求從 PRD / Spec 生成驗收時，使用可用的 `$project-evals` 更新本次受影響的
用例和檢查綁定，並把套件、來源、測試數據及腳本納入驗證輸入。沒有這套格式的項目沿用原有驗收，
不將安裝新 Skill 或補齊整套文檔設為維護前提。

### 3. 記錄範圍，執行修改

為本輪變更建立輕量運行記錄，使用 [檢查與 Hooks 協議](references/checks-and-hooks.md) 中的 `begin`。它只保存文件基線、檢查結果和會話關聯，不復制產品規格；運行目錄被忽略，不作為項目事實源。

沿用已有工程、技術棧、入口和狀態；修改本輪要求及直接受影響的實現。已有計劃適用時繼續更新同一份計劃與任務，小修改不強制新建 Plan、PRD 或完整文檔鏈。

實現中發現產品含義與原約定衝突時，核對來源及確認關係；不能為了遷就代碼而倒改規格。調整本輪文件範圍時重新核對基線，不能把已經修改後的文件冒充修改前狀態。

### 4. 驗證實現，也核對文檔的實際含義

用 `run-check` 記錄真正執行的檢查，方法與本輪可觀察行為對應：界面改動檢查實際操作，接口改動檢查請求、響應與相關調用，腳本改動檢查輸入、輸出及退出結果。只覆蓋新行為與直接受影響的舊路徑，單獨的語法檢查或 HTTP 200 不代替行為驗證。複用已有、輸入未變的有效證據；新增需求不自動證明以前未檢查的路徑已通過。

前端變更應對照代表性來源核對業務名稱，並實際沿變更入口查看目標對象/頁籤、保存後的結果與返回位置；按設計檢查目標視口、必要的列表定位或信息比較。既有鏈接受影響時核對替代落點。界面名稱調整不得改寫原始記錄或把待批准、已批准、已執行等不同業務狀態合併。

已採用 evals 時，以檢查 ID 對應運行收據，並在正式記錄關聯 eval ID；同一個命令覆蓋多條用例時仍須
核對各項斷言實際執行。來源、用例或數據變化導致的舊證據標為過期；manual 驗收記錄實際操作，不用
空成功命令替代。結構校驗與行為驗收分別報告。

在已有驗證記錄中寫入變更 ID、實際方法、看到的結果和未驗證項。保留歷史未驗證狀態及其當時適用條件，必要時說明本輪新增了哪一項證據。按需要同步演示路徑與恢復方式。

隨後對照當前需求，人工或由當前 Agent 審閱：文檔是否描述了真實的新行為，直接受影響的入口、調用方和共享狀態是否一致，未涉及的業務規則是否保留。`check` 只能檢查文件、範圍和證據有效性，不能證明業務含義一致。

使用 `finish --review <具體核對結果>` 收尾。檢查失敗時修正實際問題；未運行或無法驗證時如實交付待驗看狀態，不標成完成。

### 5. 交付

說明用戶現在能做什麼、改了哪些實現與文檔、驗證了哪些路徑，以及剩餘限制。給出已有項目的入口；不另建 `v2`、`new` 或日期工程。

當前授權範圍完成即停止。接下來在同一會話提出的新需求重新確定範圍，下一次會話從更新後的現有文件接手。

## 檢查資源

- [變更與文件維護](references/change-maintenance.md)：變更分類、當前事實、歷史、跨會話接手。
- [檢查與 Hooks 協議](references/checks-and-hooks.md)：三者分工、運行記錄格式、命令、證據失效與事件處理；實際腳本為 `scripts/maintenance.py`。
- [項目接入](references/project-integration.md)：僅在配置或修改 AGENTS / Hooks 時讀取。

`scripts/maintenance.py` 使用 Python 標準庫。其檢查結果與 Skill 的語義判斷分開報告；不調用付費模型、不安裝參考框架、不依賴真實後端。
