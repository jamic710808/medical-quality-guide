# 用體驗原型對齊未來使用流程

**原型是雙方討論未來使用方式的工具。** 它要讓人直觀看到：誰在什麼情境下進入系統，看見什麼、操作什麼，系統如何回應，下一步去哪裡，最終得到什麼。藉助 AI 加快設計與生成，完成程度由本輪溝通目標決定。

優先表達用戶與甲方希望呈現的體驗。先把需求組織成一套相互配合的功能與頁面，再用場景檢驗這套設計；不把需求條目或單條鏈路分別做成孤立的小應用，也不擴展為全套後臺模塊、業務狀態機或管理表單。技術實現只需支撐本輪整體體驗，模擬結果可以預置。

**實現可以簡化，未來使用方式仍須認真設計。** 面向日常工作的系統頁面，應考慮用戶怎樣定位記錄、比較信息、連續處理與返回工作，不能因為採用 HTML 或只有少量樣例，就將頁面做成功能卡片和說明文字的縱向堆疊。

## 業務表達心法

**讓客戶從呈現的業務處境和結果中看懂原型解決什麼問題、回應什麼需求。** 這是設計取捨與表達效果的要求，不是固定的界面形式。

- 按客戶真實的角色、業務對象、困難和預期改善組織場景、內容與信息主次。每個主要場景都應能說明需求依據、要解決的問題，以及客戶在原型中能看見的處理方式或結果；對應關係簡短記在 03 設計記錄中，不要求需求與頁面一一對應。
- 用有代表性的業務內容、關鍵差異、前後變化和結果呈現體現價值。只寫功能名稱或“提效、賦能、閉環”等口號，不能代替這件事；缺乏依據的效果和模擬數字不能寫成真實成果。
- 需求對應關係用於指導設計和審閱，不要求在頁面上增加“痛點—需求—價值”說明區、需求編號、按鈕或對話。靜態展示、比較、工作臺、列表或交互流程都可以；只有業務體驗需要用戶操作時才安排相應交互，保留用戶指定的呈現意圖。
- 頁面語言使用客戶熟悉的業務對象、任務、動作與狀態，避免包裝性黑話、空泛口號和無業務必要的模型術語。客戶行業的專業詞彙及確實有助於理解的技術名稱可以保留，不機械套用禁詞表。
- 首次生成前核對主要業務名稱的來源；有名稱的設備、物料等不能只顯示內部代號。保留用戶確實使用的業務編號及原始依據，名稱缺失不猜寫。具體命名與詳情導航按 [應用產品設計方法](references/product-design.md) 執行。
- 助手的需求分析、推理和設計步驟留在工作過程與設計記錄中，不直接充當業務界面的結構或文案。例如“先看清問題，再進入下一步”不能替代具體的業務內容；真實業務確有操作順序時，應表達那個具體順序。

例如，訂單履約場景可以通過受影響的訂單、缺料情況、交期影響及處理結果，讓客戶理解系統如何幫助處理交付風險；不必額外設計一個講解“需求是什麼”的按鈕或聊天流程。此例只說明設計思路，不規定其他項目的頁面結構。

## 輸入與目錄

- 輸入包括已有需求文件、溝通中的決定，以及用戶希望呈現的方式、參考頁面或演示重點。資料格式和數量不構成門檻；呈現方式未明確時先結合上下文提出具體方向。
- 不要求先補 PRD、詳細 UI 稿或後端架構。不把原型採用的組件、模擬規則或流程假設自動升級為正式系統設計。
- 先讀項目指令、指定資料和直接相關的既有頁面。只設計時交付設計；已授權生成原型時繼續完成演示載體與必要檢查。只有會實質改變溝通目標或核心體驗、且上下文無法解決的問題才詢問，不增加固定的逐階段審批。
- 按 [目錄與產物約定](references/output-contract.md) 使用工作區的 01—04 目錄。01/02 是已有需求輸入，03 保存體驗設計與驗看記錄，04 承載可點擊頁面。缺少 01/02 時直接使用指定資料，不重新整理資料或補空目錄。

首次準備預覽環境時讀 [安裝說明](INSTALL.md)。需要選擇實現方式或增加依賴時讀 [技術棧說明](references/stack-selection.md)；第三方心法來源見 [來源說明](references/provenance.md)。

## 第一步：明確這輪要與甲方對齊什麼

按任務定向讀取資料，區分已表達的需求、已確認決定、我們提出的呈現方案和待討論假設。保留真實業務邊界，不補造事實或確認結論。

先用簡短描述明確：

- 誰會使用系統，在什麼具體情境下開始，當前哪裡不便。
- 這是日常工作的應用頁面、用於講解的展示頁，還是其他明確形態；系統頁面還需瞭解主要任務頻率與記錄規模，未知部分作為設計假設記錄。
- 我們希望用戶未來如何完成這件事，系統準備替他處理什麼，哪些地方需要他判斷或操作。
- 本輪需要甲方看懂、比較或確認什麼，例如操作順序、信息呈現、結果形式、崗位交接或功能範圍。
- 為回答這些問題，哪些場景需要演示，哪些內容暫不展開。

先彙總本輪提供的需求與功能看板，保留來源，明確核心需求、關聯需求及暫不展開的內容；不能只挑一條容易演示的鏈路就遺漏其他核心需求。展示深度按溝通價值和用戶要求選擇，不以全部需求都做成完整業務模塊為默認目標。

用戶要求根據需求生成整體原型、且未縮小範圍時，已提供的主要功能方向默認都納入整體設計和必要展示。可以簡化模擬數據與實現深度，不能自行省略核心需求或切斷其關聯；局部迭代仍只處理用戶指定內容及直接影響。

## 第二步：形成原型的整體系統設計

使用 [體驗設計記錄模板](references/design-template.md)，在同一份 `docs/03_prototype-design/design.md` 中先說明：

- **需求與功能歸屬**：相關需求怎樣組成有業務意義的功能，哪些功能共用信息、互相支持。每項本輪核心需求都有歸屬和可見結果；不把需求清單直接當菜單，也不強制一項需求對應一個頁面。
- **業務對象與角色**：用戶共同處理什麼對象，這些對象有什麼關係，各崗位關注、補充或決定什麼。不同功能引用同一業務對象時，名稱、含義和當前情況一致；只說明體驗所需的業務關係，不設計數據庫或後端。
- **功能之間的配合**：哪些功能獨立使用，哪些並行、交叉或相互依賴，處理結果怎樣影響其他工作和原來的業務判斷。不能把所有工作強排成一條流水線，也不能讓相關功能各自維護互不相干的結果。
- **頁面與入口組織**：按用戶工作安排總體入口、頁面職責和關聯訪問方式，讓相關功能在合適的業務上下文中共同出現。整體設計不等於把所有功能塞進一頁，也不預定統一隊列、側欄、工作臺或對話形式。
- **共享狀態與結果**：明確關鍵變化影響哪些信息、頁面或崗位，哪些狀態含義必須區分，用戶最後能獲得什麼業務結果。只展開會影響本輪理解的部分，不補全量狀態機或所有異常。

用簡短說明、表或關係圖表達即可，不要求同時製作多套產物。進入頁面實現前，應能從這份記錄看清需求歸屬、整體結構、功能配合與關鍵變化的影響；說不清的部分先補設計或標明待討論假設，不靠增加菜單掩蓋缺口。

整體結構明確後，再選擇代表性使用場景細化和檢驗，包括設計中實際存在的多入口、崗位交接或跨功能變化。場景可以並行、交叉、回到已有工作；它們是同一系統的使用方式，不是彼此獨立的產品。需要說明操作經過時寫簡短故事板：

**觸發情境 → 用戶看見的信息 → 用戶操作 → 系統反饋/結果 → 下一步或結束。**

每一步寫清角色、所在頁面、實際輸入與可見結果，以及如何使用或改變整體設計中的信息。沒有用戶輸入或動作的展示環節，記錄其信息與結果即可，不為了填故事板補操作。結尾說明原業務問題得到什麼結果、還剩哪些條件；一次事項完成不能自動代表整個業務目標完成。

明確區分用戶動作和系統工作。需求希望系統整理、檢索、分析或生成的內容，可以用預置結果呈現這種未來體驗；不要為了省實現而改成讓用戶逐字段填完，再點擊“保存”的另一種流程。反過來，需求本來需要人工判斷或確認，也不能在原型裡表現為系統擅自完成。

“藉助 AI 構建原型”不等於產品必須是聊天界面。是否採用對話、工作臺、列表、分步引導或其他形式，按需求和用戶的呈現意圖決定。

## 第三步：設計頁面空間、交互與視覺表達

**設計系統頁面前，讀取並應用 [應用產品設計方法](references/product-design.md)**，把整體業務關係落實為頁面職責、主工作區、輔助信息、列表瀏覽、滾動與操作承接。局部修改只讀取與改動相關的部分，不重做無關頁面。

結構與交互選擇明確後，再讀取並應用 [Emil 設計心法](references/emil-design-eng.md)，打磨適用的組件反饋、動效和細節；它不替代信息架構與產品交互設計，也不要求增加動效庫。

在工作區的 `docs/03_prototype-design/design.md` 簡短記錄：

- 頁面在整體系統中的職責、承接哪些需求和相關功能，首屏必須讓人看懂什麼，必要操作和結果放在哪裡。
- 頁面的空間結構與信息主次：哪些需要同時看到，哪些常駐，哪些按需展開；所選形態如何支持任務，不只列組件名稱。
- 主要列表的記錄規模或假設、定位方式、默認順序及分頁或其他瀏覽方式；頁面滾動與局部滾動怎樣分工。不能因樣例少就省略真實使用所需的列表設計，也不機械要求所有列表分頁。
- 頁面之間如何前進、返回和交接；返回時保留哪些工作上下文，頁面提供的下一步由什麼工作或等待狀態承接。
- 詳情按哪些實際任務分組，是否需要頁籤；主要鏈接/按鈕落到哪個對象、頁面和頁籤，保存、關閉或返回後看到什麼。簡單任務不強拆頁籤，不能照抄後端模塊或固定案例佈局。
- 具體呈現方案：關鍵內容、示例文案、結果樣式和必要的頁面草圖。只寫“簡潔、現代、遵循最佳實踐”不足以指導生成。
- 用戶提供的參考或品牌要求，以及統一的字號層級、對比度、密度、間距和必要反饋。設計應適合實際展示尺寸，不能靠大量小字、淡色文字或裝飾留白掩蓋重點。
- 影響本輪體驗的狀態與分支。只展開會改變用戶判斷的內容，不默認製作全量空、錯、加載和權限狀態矩陣。

業務頁面使用未來用戶能理解的語言。需求追蹤編號、原型假設、實現限制和驗看記錄留在 03 文檔，不默認做成主導航或常駐說明牆；用戶用於定位的業務編號、原件編號與來源位置按任務保留。確實影響當前業務判斷的缺失信息、證據與審批條件，應在相關位置清楚呈現。用戶明確要求輔助講解頁時可以提供，並與業務操作頁面區分。

保留一個剋制的演示標識即可；不要把每個操作都變成對原型實現方式的解釋。既有原型需要調整時，按本輪決定記錄直接受影響的保留、新增、替換或移除項。

## 第四步：用最少實現支撐選定體驗

頁面方案明確後再選擇實現方式。**新建默認使用多頁面 HTML、共享 CSS 和必要的原生 JavaScript**，無需先初始化 React 或安裝組件庫；只需一個頁面的場景也不強行拆頁。頁面跳轉、彈窗、抽屜和局部更新按未來使用方式設計，不把每次操作都變成跳頁。

沿用已有原型的技術棧和入口，不因默認值改變而自動遷移。只有選定體驗涉及大量聯動狀態、複雜編輯或拖拽等交互，且框架能明顯減少實現成本時，才考慮 React 等方案，並在設計記錄中簡述原因；Vite 可按需用於預覽和資源構建。詳細取捨見 [技術棧說明](references/stack-selection.md)。原型技術不預定正式產品的選型，組件庫也不替代頁面與體驗設計。

按目錄約定在 `docs/04_frontend-prototype/` 創建演示工程，或更新已有唯一工程：

- 使用有代表性的模擬內容、預置結果和少量前端狀態。可以預設場景或採用確定性結果，無需實現真實分析、調度或審批引擎。
- 按同一份整體設計生成頁面，共用業務對象、模擬數據和狀態含義。關鍵變化在直接受影響的頁面與結果中一致呈現，不能只更新一處狀態或成功提示；可用預置的前後場景表達，不追求生產級數據模型、全量 CRUD、完整狀態機或跨崗位管理系統。
- 表單只要求未來用戶在此步驟確實需要提供的內容。不為“看起來完整”統一增加記錄人、依據編號、審批、日誌或多階段確認。
- 會影響需求理解的權限或業務約束要表達清楚，但不因此搭建真實鑑權與流程引擎；可通過預置身份、場景或結果展示。原型中的擬議規則不得寫成甲方已確認。
- 演示之外的功能可以不出現，或清楚標為本輪未展開；不要用無響應按鈕冒充可體驗功能。也不要為了讓每個菜單都可用而擴展本輪範圍。
- 模擬數據集中維護，相關對象保持一致。頁內交互先用內存狀態；跨頁只傳遞選定場景所需的信息，可用 URL 參數或會話級存儲，避免跳頁後丟失前一步的選擇。採用會話級狀態時提供簡單重置入口，不承諾刷新即恢復，也不建立持久業務數據層。
- 所選搜索、篩選、排序和分頁應實際作用於模擬記錄；用足以展示所選瀏覽方式的內容驗看，並保留必要的返回上下文。不能用無效分頁控件或永久只有首屏的樣例冒充已設計的列表體驗。
- 保留基本可訪問性、清楚的反饋和必要的焦點/關閉行為，尊重減少動態效果設置。
- 不引入真實後端、業務接口、密鑰、數據庫或外部執行動作；不為本輪原型補整套產品規格和技術架構。

## 第五步：按溝通目標驗看

先對照整體設計核對需求歸屬，再從未來使用者的視角體驗代表性場景，檢查功能組合在一起是否講得通：

1. 本輪核心需求是否都有具體呈現，客戶能否從系統中的業務內容和結果看懂解決什麼問題？明確本輪未展開的內容，不用功能名稱或口號代替實際體現。
2. 頁面入口和職責是否清楚，相關功能能否在同一業務上下文中配合？從不同入口查看同一對象、切換崗位或返回原工作時，信息和狀態是否一致？只檢查設計實際包含的這些情況。
3. 關鍵處理或條件變化後，相關頁面與判斷是否反映結果？是否仍有已處理事項卻完全不影響相關業務信息的斷點？保留尚未滿足的條件，不以事項關閉冒充業務目標完成。
4. 不依賴長篇口頭解釋，能否理解當前情境、系統回應、已有結果與必要操作，用戶工作與系統工作是否分明？不要為滿足驗看而額外添加按鈕或對話。
5. 按 [應用產品設計方法的驗看項](references/product-design.md#6-用操作任務檢查設計不以內容齊全代替可用)，檢查實際涉及的列表瀏覽、頁面滾動、比較、返回上下文和下一步承接。能否連續完成工作，而非只讀完一組卡片？
6. 關鍵信息是否看得清，佈局與文案是否支持本輪體驗？是否混入包裝性黑話，或把助手的工作步驟、模擬機制當成用戶流程？
7. 甲方能否據此指出整體組織、功能配合、流程或呈現哪裡與預期不同？擬議方案與已確認需求是否分清？

再做支撐演示的最小技術檢查：通過本地預覽打開頁面，檢查資源加載、頁面鏈接、本輪演示路徑、必要返回和恢復操作；跨頁傳遞了狀態時，確認前後選擇一致。僅在實際採用構建或類型檢查工具時運行相應命令，不為純 HTML 原型補裝工具鏈。檢查約定的展示尺寸；只有本輪要討論移動端體驗時才增加移動端驗看。不默認擴展為完整迴歸、壓力測試或全量業務規則驗收。

優先使用內置 Browser（`iab`）或項目允許的獨立瀏覽器。用戶明確要求自己驗看或不運行瀏覽器自動化時，按該要求交付可訪問入口和演示路徑，標明未檢查項；不要為了滿足 Skill 再運行自動化。工具不可用時也如實說明，不虛構查看結果。

在 `docs/03_prototype-design/verification.md` 按本輪核心需求簡記實際入口、觀察到的業務結果與頁面操作體驗、必要運行檢查及未驗證項，不能只寫“整體鏈路通過”。編譯通過不能證明原型表達清楚，助手驗看也不能代替甲方確認。修正實際觀察到的問題，僅複查受影響內容。

## 第六步：依據溝通反饋迭代

收到反饋後，先判斷差異發生在需求理解、整體功能組織、未來使用流程、信息呈現還是視覺表達。涉及共用對象、功能關係或狀態含義時，先更新整體設計，再同步直接受影響的頁面；局部反饋只改對應內容，不每次重做整個原型。不要直接把所有反饋轉成新增模塊或增加字段。

在同一份 `design.md` 中記錄實際反饋來源、涉及體驗、修訂和確認狀態；更新同一個演示工程。沒有甲方反饋時保留待討論項，不編造批准或等待反饋才交付已完成的本輪演示。

## 交付與停止

交付可訪問的演示入口、簡短的體驗路徑、03 的整體設計與場景記錄、04 的頁面源碼和啟動說明。README 說明運行目錄、如何開始體驗、模擬內容及恢復方式；設計與工程入口相互鏈接。

當本輪核心需求在整體原型中有歸屬、相關功能與結果一致、頁面組織與操作能支撐代表性工作，且必要運行檢查已完成或未檢查項已明確，即交付等待反饋。**原型範圍內的整體體驗可討論，是完成標準；完整系統實現不是本技能的目標。** 不把頁面做出、技術檢查通過或一次演示，寫成正式功能已經交付、技術方案已經確定或甲方已經接受。

已知的核心需求遺漏、必要入口不可達或相關結果矛盾不滿足完成標準，應先修復，不能僅登記為“未驗證”後宣稱完成。用戶要求自己驗看或工具確實不可用時，可以交付待驗看的版本，但須區分未檢查與已發現的問題。
