# 從業務需求到可操作的應用界面

在整體業務設計之後、關鍵頁面實現之前使用，適用於體驗原型和正式應用的首次構建、局部迭代。用戶明確要求的講解頁、營銷頁或大屏按各自用途設計。這裡約束產品體驗，不決定技術棧、後端能力或交付範圍。下文“設計記錄”指項目已有的前端設計或相關 Feature Plan；原型使用 03 中的 `design.md`，正式工程不必另建原型目錄。

## 1. 從日常工作確定頁面職責

先結合需求判斷使用者的任務、頻率、共同處理的對象和通常面對的信息量。區分已知事實與設計假設：沒有實際記錄規模時，在設計記錄中寫明用於設計的假設，不把幾條演示數據當成業務上限。

用“用戶來到這裡要完成什麼工作”定義頁面，再決定信息和操作。列表負責定位與篩選，詳情負責理解和處理選定對象，比較負責看清差異，工作臺負責持續操作與結果反饋；一頁可以承擔相關職責，但不能只把所有功能各放一張卡片來替代佈局設計。

應用頁面、講解頁面和營銷頁面的組織依據不同。應用頁面優先呈現當前對象、狀態、可用操作和結果；有講解用途的頁面可以按閱讀順序展開。HTML、單頁實現或模擬數據都不意味著要把系統做成長篇說明頁。

沿用整體設計中的全部核心需求和對象關係。代表性場景用於檢查同一個系統的使用方式，不能為做透一個案例而自行刪去其餘已納入範圍的主要功能。

### 先確定用戶看見的業務名稱

實現菜單、標題、按鈕和詳情之前，從本輪資料中核對主要對象的稱呼、編號及狀態含義，在設計記錄中簡記“來源字段或約定 → 顯示名稱 → 編號用途”。複用已有業務詞彙，不另建全量術語庫，也不逐個詢問已有明確依據的名稱。

- **名稱有依據**：從客戶用語、主數據或已確認業務定義取得名稱。例如臺賬記錄 `EQ-17` 的名稱為“二號包裝線”，設備列表和問題標題應先讓人看到“二號包裝線”，編號用於區分與追溯。不能根據代號自行猜一個業務名稱；缺少名稱時顯示“設備名稱待核實”及原編號。原型自擬名稱屬於模擬內容，記錄其性質，不冒充來源事實。
- **區分標識用途**：用戶日常確實用來定位的訂單號、工單號、批次號可以保留為主要標識；內部數據庫 ID、運行 ID、字段鍵和工程代號不充當業務名稱。版本、提取方式等低頻技術信息按需展開；面向技術人員的頁面按其實際任務保留必要術語，不機械禁止所有編號或英文。
- **按任務命名**：導航、頁籤和主操作說明用戶查看或處理什麼；不要直接複製 API、Feature、數據表或助手推理階段的名稱。“事實與條件”“結果迴流”不能僅因內部這樣分層就成為菜單，應按場景表達為“交付準備”“更新訂單進展”等；這些是示例，不是固定替換詞。
- **狀態不能只翻譯字面**：結合對象解釋 `pending` 是待檢驗、待審批還是待回覆。待批准、已批准、已執行分別表達；把“生成建議”命名為“安排發貨”會製造錯誤承諾。名稱、按鈕作用和可觀察結果必須相符。
- **同一概念沿旅程一致**：核對列表、詳情、關聯選擇器、圖節點、方案和處理記錄中直接相關的稱呼。顯示名稱和穩定業務身份分開；歷史內容按對應版本解釋，原始證據和來源字段保留原文，不用全局字符串替換改寫事實。

## 2. 先定空間與交互，再選組件和視覺

為關鍵頁面在已有設計記錄中用簡短草圖、表或文字說明：

- **主工作區**：主要任務、需要同時看到的信息和結果，佔據什麼位置與空間。讓判斷和操作所需的內容靠近，避免重要結論擠在窄側欄，主體卻只展示說明。
- **導航與上下文**：如何知道所在位置、當前業務對象，怎樣前往關聯工作並返回。按實際需要保留全局導航、頁內切換或對象摘要，不固定套用側欄或工作臺。
- **輔助信息**：證據、歷史和補充細節何時需要，適合並列、展開、抽屜還是獨立頁面。需要頻繁對照的內容不要反覆藏進彈窗，偶爾查閱的長資料不必全部鋪在主工作區。
- **交互模型**：哪些動作改變選定對象、篩選範圍或業務結果；切換後什麼保持不變，什麼必須更新。按鈕名稱、附近說明和實際結果要表達同一件事。

結構選擇要能說明如何幫助完成任務。表格適合按共同維度掃描記錄或比較差異；卡片適合有獨立內容結構或可直接操作的對象；分欄適合需要同時保留上下文的處理；獨立詳情適合展開一個對象。按當前任務取捨，不把這些形態規定為所有頁面的必選項。

### 詳情頁籤和入口落點一起設計

同一對象有多組相對獨立的閱讀或處理任務時，考慮頁籤；需要同時比較的信息放在同一視野，簡單表單或短詳情不必拆籤。不能把所有內容堆成長頁，也不能為了形式完整給每個鏈接都加一組頁籤。

- 按用戶任務劃分，例如資產詳情可分“使用安排 / 維護記錄 / 相關資料”，而不是照搬後端模塊。數量、名稱和分組來自當前業務，不統一套用某個案例的五個頁籤。
- 名稱、關鍵狀態和必要主操作作為對象上下文保留。默認籤承接最常見任務；“查看檢驗記錄”應直接落到對應記錄或頁籤，“補充記錄”保存後應能看見新記錄，不能一律跳回概況或讓用戶重新查找。
- 在設計記錄中對主要入口簡記：**從哪裡點擊 → 哪個對象/頁面/頁籤 → 能看到或完成什麼 → 關閉/返回去哪裡**。結合任務決定刷新、前進後退和返回列表時需要恢復的對象、頁籤及篩選，不規定必須使用某種狀態存儲。
- 迭代時核對原鏈接和直接調用方；有實際舊鏈接或書籤時提供對應落點或說明替代路徑。頁籤重命名不應意外改變對象身份、業務狀態或保存行為。

關係圖等專用視圖也按用途設計：依據已有對象與關係展示，並區分語義關係、來源關聯和待核實連接；選擇、拖動、縮放與編輯關係是不同能力。只讀圖可支持查看和移動位置，不應出現讓人誤以為能創建業務關係的無效控件。參考項目的截圖或樣式不能代替本項目數據與交互的驗看。

需要參考時，定向查看與當前任務相似的真實產品頁面或用戶給定樣例，提取具體做法及其適用條件。記錄實際查看的來源；未查看的不能寫成已研究。參考幫助解決佈局或交互上的具體不確定性，不要求固定數量的競品、雙主題或多輪視覺方案。

## 3. 列表按記錄規模和定位任務設計

訂單、事項、附件等記錄集合會隨使用增長。為本輪主要列表明確展示哪些字段、默認順序、如何找記錄，以及超出當前視口後的瀏覽方式；只提供與用戶任務有關的篩選和操作。

| 使用情況 | 設計取捨 |
| --- | --- |
| 持續增長、需要精確定位、核對或返回的業務記錄 | 通常採用分頁，結合必要的搜索、篩選與排序；避免默認把全部記錄鋪成整頁長列表 |
| 數量少且有明確上限的選項或記錄 | 可以完整展示，在設計記錄中說明範圍；不為形式完整增加無用分頁 |
| 以連續閱讀為主的動態或時間記錄 | 可選加載更多或連續加載，保留定位和返回方式；不能因實現省事默認用於所有業務列表 |

選擇分頁時，確定合理的每頁數量、翻頁方式及當前範圍。頁碼、範圍、總數與篩選後的實際結果一致；只知道是否還有下一頁時，不偽造總數。篩選改變後回到有效頁，不能留下空白的失效頁碼。搜索、排序、分頁共同作用於同一份結果，不只改按鈕或數字。

用足以體現所選瀏覽方式的代表性記錄呈現體驗。例如選擇分頁，就應能實際翻到另一頁並打開其中的對象；不必生成大量無意義數據。原型可使用模擬記錄；正式工程沿用實際數據和接口合同，不以模擬分頁替代承諾的能力。

表格的行高、列寬、字段主次應支持快速掃描。優先保留識別對象和當前決策需要的字段，將長描述放到適當的詳情位置；不通過無限增高行或縮成小字容納全部內容。記錄較長、表頭容易離開視口時考慮固定表頭，固定操作不能遮擋內容。

## 4. 明確視口與滾動的分工

按約定展示尺寸檢查首屏的業務重點、主操作和上下文。應用可以滾動，但用戶不應為尋找篩選、當前對象或下一步操作反覆穿越大段無關內容。

在設計中說明是整頁滾動，還是由主要記錄區、證據區等局部滾動，以及理由。長文閱讀可以整頁滾動；持續處理記錄時可保留必要導航、篩選或對象摘要。不要把所有頁面強鎖在一屏，也不要給每張卡片增加獨立滾動條。

需要比較的方案，應讓關鍵差異在同一比較視野中容易找到，詳細依據再按需展開。不能僅因為每個方案都有相同字段，就認為縱向堆放幾張大卡片已經支持比較。

## 5. 保持操作上下文與工作承接

- 從列表進入對象再返回時，保留任務需要的篩選、排序、頁碼和合理的列表位置；刷新或前進後退的恢復範圍按本輪設計實現。可用 URL、少量會話狀態或瀏覽器原有能力，不為瀏覽狀態新增不必要的存儲層。
- 同一對象在不同頁面、頁籤和崗位入口中保持身份與業務結果一致。新事實應更新直接受影響的原因、方案條件、下一步和證據，而不只修改狀態標籤。
- 頁面聲稱的“下一步”應有相符的承接：已安排的事項能找到對應崗位和工作內容；尚未安排的應明確，並提供本輪需要的發起或補充方式；依賴外部處理的說明等待誰和什麼結果。不能把用戶帶到空列表後再讓其返回原頁面。
- 在同一原型體驗中演示不同崗位時，讓用戶知道當前以什麼角色看待操作及結果，不要求真實登錄。選擇方案、崗位確認、接受和業務結果按實際需要區分；不為每一步統一增加一次“確認並記錄”彈窗。
- 交互使用未來業務中的語義。模擬機制留在 03 與 README，不把“點擊後系統會呈現……”當成每個業務動作的說明；只解釋會影響當前用戶決定的後果和條件。

例如：用戶在篩選後的第二頁打開一張訂單，比較辦法並形成倉儲事項，倉儲核對結果後，訂單判斷與相關方案條件隨之更新；返回原列表時繼續原來的工作位置。這個例子說明承接和上下文，不規定所有項目必須有這些崗位或步驟。

## 6. 用操作任務檢查設計，不以內容齊全代替可用

優先檢查與本輪設計直接有關的情況，不展開全套狀態矩陣：

| 要驗證的問題 | 可觀察的證據 |
| --- | --- |
| 頁面是否支持當前工作 | 能識別所在頁面和對象，找到主要任務與必要操作，不依賴長篇口頭講解 |
| 名稱是否來自業務且足以辨認 | 對照代表性來源，名稱與編號對應正確；缺失名稱未被猜寫，狀態未被誤譯；同一對象在直接相關入口仍可識別 |
| 詳情分組和按鈕落點是否合理 | 通過主要鏈接進入預期對象和頁籤；保存後看見對應結果；共享上下文、返回及約定的刷新恢復正確 |
| 列表增長後是否仍可定位 | 用所選分頁或加載方式找到記錄，範圍和數量正確；少量固定列表則檢查其上限假設 |
| 頁面結構是否支持判斷 | 在目標尺寸下看清關鍵結論；比較差異無需在長段內容間反覆翻找 |
| 返回是否能繼續原工作 | 從非初始列表狀態進入詳情再返回，所需篩選、頁碼和位置保留 |
| 下一步是否有承接 | 跟隨頁面明確提供的下一步，能到達相符的工作或清楚的等待狀態 |
| 變化是否影響相關判斷 | 處理結果能在直接關聯的頁面、方案條件和後續事項中一致體現 |
| 專用視圖是否兌現所表達的能力 | 採用關係圖時能看到來源支持的節點/邊，完成所提供的選擇、拖動或查看操作；只讀展示沒有被當作業務關係編輯 |

根據實際觀察修正設計與頁面，僅複查受影響項。用戶要求自行驗看時，交付上述適用路徑並標明未檢查，不改成強制瀏覽器自動化。把真實觀察與尚待用戶測試的部分分別寫入已有 `verification.md`。

本指引將已審閱的全局設計材料中適用的思想重新組織為原型方法，來源與取捨見 [來源說明](provenance.md)。它不依賴另外安裝或執行那些 Skill。
